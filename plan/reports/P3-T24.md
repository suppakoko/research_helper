# P3-T24 report: prompt registry with versioned prompt files

## Verdict

The registry is built and unit-tested, with the bundling step left unwired on purpose. The five prompt files are transcribed word for word from `docs/12` §3–§7, and a test re-reads `docs/12` and checks each file against it. The `PaperSummary` schema file is in place. The registry reads each file's header, checks all of §17.3's load-time rules plus several more, fills in the `{{PLACEHOLDER}}`s in one literal pass, and escapes `<<<` in every value it inserts. The checks are 56 unit tests, and a mutation sweep altered the code or files 18 times; the tests caught all 18. The type check, both lint commands and the unit and contract suites exit 0. Three things are not done:
- **Step 7 and the matching finishing condition ("the built bundle loads all five prompts").** Both depend on the open line about bundling, so neither was attempted.
- **`typings/prompts.d.ts`.** Not created, because it only exists if the open line picks a loader.
- **"Byte-identical to `docs/06` §6.2".** This cannot hold while `npm run lint:check` passes. The repository's formatter, Prettier, rewrites the raw block, and only `*.md` is excluded from formatting. The file therefore holds the block as the repository's own Prettier settings print it, and the test asserts exactly that. The coordinator decides whether to add the one ignore line that would allow raw bytes.

Separately, the open line's recommendation, as written, would break the integration test bundle and the unit test runner. Details are in the bundling section below.

## Steps stopped by the open line, and what the `.md` loader investigation found

**Steps stopped:**
- **Step 7.** Making the `.md` files reach the bundle, and proving it on the built artifact.
- **Step 4, the "fails the build" part.** Today a malformed file fails `npm run test`, because the unit test reads the real files. `npm run build` will only fail on one once the seam is wired.
- **Step 6, the constant form of `PROMPT_VERSIONS`.** It can only be a module-level constant once the text is bundled. Until then it is `createPromptRegistry(files).versions`. The module comment names the seam: whichever bundling approach is chosen passes `PromptSourceFile[]` to `createPromptRegistry` once.
- **`typings/prompts.d.ts`.** Not created.
- **`npm run build`.** Not run. Two Zotero processes, 32548 and 35088, had `.scaffold\test\profile` in their command lines. Nothing was killed. The new module is not imported from `src/index.ts`, so it is not in the bundle.

**Findings.** Read from the installed zotero-plugin-scaffold 0.9.2 and esbuild 0.28.2, and tried out on throwaway files in the scratch directory. No project build setting was changed.

1. **The recommended option is accepted by the main build.** Scaffold types `build.esbuildOptions` as esbuild's `BuildOptions[]`. esbuild's `Loader` type includes `"text"`, so `loader: { ".md": "text" }` type-checks. Scaffold's `resolveConfig` passes each option through unchanged, apart from rewriting `outfile`/`outdir`. Tried: without a loader, esbuild fails with "No loader is configured for ".md" files". With the text loader, the file is inlined as a string.
2. **The integration test bundle would break under that recommendation.** Scaffold's `TestBundler.bundleTests` builds `test/integration` with its own fixed esbuild settings (entry points, output directory, `bundle`, `target: "firefox115"`, `metafile`). It does not read `build.esbuildOptions`. The `test:*` hooks fire after bundling, so nothing can inject a loader there. Integration specs already import `src/` (for example `createScope` from `src/bootstrap/container`). So once anything in that import chain does a plain `import x from "./x.md"`, the integration suite fails to bundle.
3. **Import attributes need no loader setting in either esbuild build.** esbuild 0.28.2 accepts `import x from "./p.md" with { type: "text" }` with no loader configured. Tried: it inlines the string. The scaffold test bundler uses the same esbuild, so this form works in both bundles. TypeScript 5.9 type-checks it with a `declare module "*.md"` declaration (tried with `module: ESNext`, `moduleResolution: bundler`). esbuild does not understand Vite's `?raw` suffix ("No loader is configured for ".md" files: p.md?raw").
4. **Vitest 5 cannot import `.md` in either form.** It fails with a parse error both for a plain import and for `with { type: "text" }`. Only `?raw` works, and esbuild rejects that form. So any approach in which the module the unit tests load imports `.md` directly also needs a change to `vitest.config.ts`, which is not in the card's Files. The current design avoids this: unit tests pass the text in. A later wiring file that holds only the `.md` imports would keep the unit tests independent of the choice.

## Contradictions

1. **The finishing condition "byte-identical to `docs/06` §6.2" conflicts with `npm run lint:check`.** `.prettierignore` excludes only `*.md`, and Prettier rewrites the raw block (114 changed lines). The file ships formatted. The test asserts the same schema with keys in the same order, and that the file equals Prettier's output for the docs block. The alternative needs `src/prompts/schemas/*.json` added to `.prettierignore`, a file outside this card's Files list. After that, copy the raw block in and switch the test to compare raw bytes.
2. **`docs/12` §17.3 has no field for declaring variables**, yet its validation rule requires every placeholder to be declared. A `variables` block list was added to the header format, which changes §17.3.
3. **`RELEVANCE_SCREEN`'s maximum output tokens is 100 × the batch size** (`docs/12` §3), so a single `defaultMaxTokens` cannot express it. The header uses `maxTokensPerItem` instead, and `resolveMaxTokens` does the multiplication.
4. **`docs/12` §3 defines a `RelevanceScreen` output schema, but the card's Files create only `paper-summary.v1.json`.** `RELEVANCE_SCREEN` therefore ships with `schema: none`. `P3-T27` will need that schema file.
5. **The version string format differs between documents.** `docs/12` §17.3 and §17.4 write `1.0.0`; the comment in `docs/06` §11.2 writes `'v1.2.0'`. The registry uses `1.0.0`; file names carry `.v1.0.0`.
6. **`cacheEpoch` and the cache key disagree.** `docs/06` §11.2 and `docs/12` §17.4 build the cache key from the full version string, `PROMPT_VERSIONS[id]`. But §17.2 says a PATCH bump keeps the cache through `cacheEpoch`, and keying on the version string would discard it on every PATCH. `P3-T26` has to choose; both values are exposed.
7. **`docs/12` declares variables these prompts never use.** §5 says `PAPER_SUMMARY_FULLTEXT`'s variables are "As `PAPER_SUMMARY_ABSTRACT`, plus", which would include `{{ABSTRACT}}`, but that prompt never uses it. §7's "Metadata as in §5" would include `ITEM_TYPE`, `DOI` and `TAGS`, which `CHUNK_REDUCE` never uses. Declaring them would break the "every declared variable used" rule, so only the variables actually used are declared.
8. **`docs/12` §1.1 rule 3's single replacement of `<<<` with `< <<` is incomplete.** A single pass over a run of four or more `<` leaves a fresh `<<<` behind. The code repeats the replacement until no `<<<` remains. The escape is applied to every inserted value, including the trusted metadata and the schema, which contain no `<<<`.
9. **`docs/12` §1 names a continuous-integration check, `scripts/check-prompt-sync.mjs`, that is not in the tree.** For these five prompts the new test does the comparison against `docs/12` instead.
10. **`lastReviewed` is set to 2026-09-09** for all five prompts. That is `docs/12`'s "Last updated" date, not a review date; the owner may want another value.
