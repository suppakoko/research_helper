# P2-T39 — DOI-family comparison pass; newest F1000Research version wins

**Findings.** A DOI is the permanent identifier a publisher gives a document. Some documents belong to one paper: its review reports, its editor's assessment, or a later version. Their DOIs share a "family stem", and before this card such documents were compared only when their titles fell into the same title block. Now the identifier pass also compares every two records whose DOIs share a stem, so these documents reach the comparison even when their titles differ. The ordinary decision rules still make every decision. The test-data script that builds the collection of record pairs for measuring duplicate detection (the corpus) now finds these pairs as well. The corpus grew from 534 to 552 pairs. All 18 new pairs are unlabelled and come from three eLife papers, and each now merges where before it was kept apart. No labelled pair changed outcome, and no pair labelled "not a duplicate" or "linked version" is merged. When F1000Research versions of one article merge, the newest version now supplies the DOI and the date. The older versions' DOIs stay on record as conflicts. In the corpus this changes exactly one merged work (F1000Research article 130932), and the other 932 groups with no family member merge byte-for-byte as before. The owner's 60-pair sample measures the same as before: precision 1.0000, recall 1.0000, both still undecided. Every static check, the unit tests and the build pass, and the 16 deliberate faults planted in the new code were all caught. **One condition is not met: three consecutive clean integration runs.** Four runs gave one clean run and three runs that each failed one test. The failing test is a light-and-dark theme contrast test in the search dialog, which waits a fixed 250 milliseconds for the theme to switch. It fails the same way on the last commit with this card's source changes removed, so the failure predates this card; it needs a decision on who fixes it.

## 1. The rule and where it is documented

- **Comparison by DOI family** (owner decision, plan/00 §6 item 366(b)). Inside the identifier pass of `dedupeRecords` (the pass before blocking by title), after the bioRxiv accession pass and before version links, every two records whose DOIs satisfy `sameDoiFamily` are proposed for comparison, whatever their titles and years. The function `doiFamilyPairs` in src/sources/shared/dedupe.ts proposes them. The pass only proposes pairs: the cascade still decides, and the group-level split at version links (`partitionAtVersionLinks`) still applies. Documented in docs/02-literature-database-apis.md §11.3 in the dated note "Decided 2026-11-10 (owner, plan/00 §6 item 366(b)): a comparison pass by DOI family". The earlier paragraph ("Neither rule adds a comparison") is kept and carries an inline "Superseded later on 2026-11-10" mark.
- **Corpus origin.** scripts/build-dedup-corpus.ts gains the pair origin `doi-family` (in `PairOrigin` and `ENGINE_ORIGINS`), and `candidatePairs` calls `doiFamilyPairs`.
- **No new DOI forms** (item 366(d)). The five forms from P2-T38 are unchanged.
- Coordinator decisions, recorded as "DECIDED 2026-11-10 (coordinator, under item 313)" in docs/02 §11.3:
  - The pass sits in the identifier pass, because a shared DOI stem is an identifier fact.
  - There is no year check, because a review report can be years apart from its paper.
  - A family of n records costs n − 1 comparisons once the group joins, because records already in one group are skipped.
  - Corpus rows found by the new origin sort after the existing origins, so no existing row moves.

## 2. The winner change

- **Owner decision** (item 366(c)): when F1000Research versions of one article merge, the newest version wins the DOI and the date, and the other versions' DOIs stay in `ids` as conflicts. This replaces the coordinator's earlier rule, in which version 1 won. Documented in docs/07-architecture-and-data-model.md §5.1 in the dated note "Decided 2026-11-10 (owner, item 366(c); P2-T39)". The coordinator's earlier note is kept, marked "(b) was replaced later the same day by the owner's decision below; (a) stands." docs/02 §11.4 carries an "Updated later on 2026-11-10" line.
- **Code.** `articleVersionOf` in src/model/ids.ts reads the stem and version number from an F1000Research article DOI. In src/model/merge.ts:
  - `newestArticleVersionDoi` picks the highest version when two or more distinct version DOIs of one article are present.
  - `unionIds` puts the records carrying that DOI first for the DOI field.
  - `merge` takes the published date and the online date from those records, and falls back to all records when they carry no date.
- Coordinator decisions, recorded in docs/07 §5.1:
  - "Newest" is read from the DOI's version number, not from any date.
  - "The date" covers both date fields.
  - The rule applies only when all version DOIs in the group belong to one article; otherwise the ordinary policy applies.
