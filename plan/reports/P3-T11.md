DOC NOTES ADDED (quoted)
docs/07 §4.3, after "3. **A missing `chatStream` falls back to `chat`** …":
"**Decided 2026-10-21 (`P3-T11`): the streaming contract.** (a) The router also calls `chat` when the adapter's `getModel(request.model)` says `supportsStreaming: false`; an unknown model streams. (b) A stream yields text chunks with `done: false` and then **exactly one** chunk with `done: true`, `deltaText: ""` and the provider's final `usage` when it sent one; completion is taken from the provider's terminal event (`[DONE]`, `response.completed`/`response.incomplete`, `message_stop`, `interaction.completed`), never from an empty delta. (c) A stream that ends without its terminal event — cut mid-frame, or a frame that is not JSON — throws `NetworkError`, never a short result. (d) A terminal event whose stop reason is a truncation throws `OutputTruncatedError` (the same class `completeJSON` throws for `finishReason: "length"`) after the text already yielded, and a refusal throws `ContentFilterError` through `mapProviderError`, because `ChatStreamChunk` has no `finishReason`; the `chat` fallback in (a) applies the same truncation rule, so a caller of `chatStream` sees one contract. (e) An error event after HTTP 200 (`docs/03` §6.2 note 4) is mapped through `mapProviderError`. (f) The request is `HttpClient.request` with `HttpOptions.onBodyText` (§7.4's choke point, its limiter slot held for the stream's life, its retry, timeout and redaction unchanged); an attempt that has delivered any text is never retried. (g) A consumer that stops iterating cancels the request through a token linked to `LLMCallContext.token`; that is not an error and nothing is thrown."

CONTRADICTIONS / FINDINGS
1. OpenAI models never stream once they are listed. `toModelInfos` in src/llm/openai/mapper.ts sets `supportsStreaming: false` to mean "not known" until P3-T13. Under the card's step 4 rule, any OpenAI model returned by `listModels()` therefore falls back to `chat()`; it streams only while unknown. Fix belongs in P3-T13's enrichment, or the "unknown" encoding should change. Not fixed: openai/mapper.ts is outside my Files list.
2. One router test no longer tests what it says. `mockModel` in test/helpers/mockLLM.ts defaults `supportsStreaming: false`, so router.test.ts's "chatStream passes a provider's own stream through" (model "mock-small") now takes the `chat()` fallback. It still passes, but only because its assertions also hold for one terminal chunk. Pass-through is now tested in sse.test.ts with `supportsStreaming: true` and with an unknown model. router.test.ts and mockLLM.ts are outside my Files list.
3. Gemini stream payloads are assumptions. docs/03 §6.3 records the Interactions event names but not their payloads. `createGeminiStreamDecoder` states three assumptions:
   - the event name comes from the `event:` line, else from `event_type`;
   - `step.delta` carries `{ delta: { type: "text", text } }`, and any other delta type is not answer text;
   - `interaction.completed` carries the interaction under `interaction`, or is the interaction itself, and is read with `readInteraction`.
   If any is wrong, a live Gemini stream fails loudly with NetworkError ("ended before its terminal event"), never silently empty. This needs one recorded stream, which P3-T30 or a gated live check could supply.
4. Long streams hit the 3-minute timeout. A stream is bounded by the same `LLM_ATTEMPT_TIMEOUT_MS` (3 min) as a plain call: the XHR timeout covers the whole stream. A trend report that streams for more than 3 minutes would end in TimeoutError. docs/01 §8.4.1 records that other plugins zero the timeout from the progress handler; that is deliberately not done here (no-hang rule). Whether streams should get an idle timeout is an open owner question.
5. The router's `chat()` fallback now throws `OutputTruncatedError` for `finishReason: "length"` instead of yielding the cut text. This keeps the `chatStream` contract the same with or without real streaming (docs/07 note (d)). It changes behaviour only for truncated answers through `chatStream`; `chat()` itself is unchanged.
6. Anthropic strict-tool streaming does not reproduce `chat()`'s text exactly. In strict-tool mode the stream yields the raw `input_json_delta` fragments, while `chat()` re-serializes the parsed tool input. The JSON is equivalent but the whitespace can differ. This is documented on the decoder; the byte-identity criterion was measured on the text mode.
7. Two stale doc claims. docs/03 §6.5 still says `Zotero.HTTP.request()` "buffers the whole response and is not suitable for streaming", which V-8 disproved. docs/07 §4.1's rationale paragraph still calls streaming "a different response contract". Not changed: docs/03 is outside my Files list, and the docs/07 paragraph is historical rationale.
8. Mid-stream error mapping uses assumed status tables. Anthropic error types map to HTTP statuses using docs/03 §11.1's types; OpenAI error codes map as rate_limit_exceeded or insufficient_quota → 429, context_length_exceeded → 400, anything else → 500. The OpenAI `error` event shape is taken from §6.1's event list, not a recorded frame.
