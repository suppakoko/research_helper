# P1-T47: Store, export and log a stack without the folder the add-on is installed in

**Date:** 2026-11-26 · **Executor:** Claude Code (agent), batch M (`plan/reports/P7-batchM.md`) · **Commit base:**
1674121, uncommitted. **State:** `TODO`; only the owner sets `DONE`.

**Why the card exists.** `plan/00` §6 item 417(b), answered "Check first" by the owner: read one error saved by an
installed build, and card a fix if a stack frame names a folder under the user's home. Batch M measured it (the
frame shapes are in `plan/reports/P7-batchM.md`, the user name replaced by `<user>`): `startup` in
`addon/bootstrap.js` loads the bundle from the add-on's `rootURI`, so every frame of the plugin's own code names it.
For an XPI in a profile's `extensions` folder that is
`jar:file:///C:/Users/<user>/AppData/Roaming/Zotero/Zotero/Profiles/<profile>/extensions/<id>.xpi!/`, under the home
folder by default, and the job queue's gate stored such a stack byte for byte.

**Caller and constructing file (rule 10).** The step is built in `src/core/errors.ts`: `reduceFileLocations`,
module-private, called first by `redact`. No caller changed; each already calls `redact`:
- `ResearchHelperError.toSerialized` in `src/core/errors.ts` (the `stack` member);
- `teardownErrorLine` in `src/core/errors.ts`, called by the scope's `onError` in `src/addon.ts`;
- `redactText` in `src/core/provenance.ts`, behind `redactRecord` (which `toJobRow` in
  `src/core/jobQueue/jobRecord.ts` calls for `JobRecord.error`) and behind `redactSerializedError` (which the
  provenance export reaches for `SourceProvenance.error`);
- `redactValue` in `src/core/logger.ts`, for an `error` in a log line's context.

## What changed

- **Docs first.** `docs/09` §2.1: the printed `redact` block gained the step, and a dated paragraph says why ("A
  file location never leaves the plugin whole", added 2026-11-26). `docs/07` §5.2: a dated note on `stack`; §10.1's
  copy of `toSerialized`: a dated comment.
- **`src/core/errors.ts`.** Before the key patterns run, `redact` now reduces every file location:
  - a `jar:` URL loses everything up to and including its `!/` (the archive's own location);
  - a `file:` URL keeps what follows its last `/content/` (the plugin's resource path), or, when it has none,
    `[file]/` and its last segment.
  So a plugin frame reads `<function>@content/scripts/research-helper.js:<line>:<col>` in every install form, and the
  function name, resource path, line and column a bug report needs are kept. The step is idempotent, leaves web and
  `chrome://` URLs alone, and runs inside the one redactor, so there is no second redactor and no second gate.
  `KEY_PATTERNS` is unchanged (eight entries, same order), and so is `SerializedError`.

## Not covered (owner question, `plan/00` §6 item 419)
