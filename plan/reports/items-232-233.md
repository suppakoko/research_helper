**Item 233: a 90-second total budget per HTTP request, retries included.**
- **Where the budget applies:** only to requests that have a retry policy, meaning a policy that lets the HTTP client try a failed request again by itself.
- **How time is measured:** on the injected clock. The injected clock is the time source passed into the client, so tests can control time.
- **When the budget starts:** when the request's first attempt is handed to the transport. The transport is the layer that actually sends the request.
- **What the budget covers:** every later attempt and every wait between attempts.
- **When the budget is spent:** the request ends with its last error.
- **Waits:** no wait starts if it would end at or past the 90-second mark.
- **Single attempts:** the budget never cuts an attempt short. Each attempt keeps its own 60-second timeout.
- **Cancellation:** it still stops the request at once. The loop checks cancellation before it checks the budget.
- **The per-source 20-second search deadline** in `stages.ts` is untouched.
- **Docs first:** the dated note in `docs/07` §7.3 was written before the code. The worst-case text was corrected to the new bound (see section 6, item 2).

**Item 232: a source refused with HTTP 429 after the retries now has its own row.**
- The Search window shows "too many requests, refused · try again in a moment" together with the database name. It appears in that source's status row and in that source's line of the panel shown when every source failed.
- The message is new: `research-helper-search-error-rate-limit`.
- The action is Retry and never Open Preferences. This matches the `RATE_LIMIT` row of `docs/08` §8.3 ("Retry now") and the item 220 rule (buttons follow each failed source's own row).
- `RATE_LIMIT` left `UNRENDERABLE_ERROR_ROWS`.
- **Docs first:** the dated note in `docs/08` §8.3 was written before the code.

## 6. Contradictions

1. **The P2-T16 failures do not come from this change.**
   - Those steps use `test/support/fixtureReplay.ts`'s multi-host client. Its clock is frozen and its waits finish at once.
   - So the time spent always reads 0, and the budget can only end a request on a wait of 90 s or more. The recorded Semantic Scholar 429 (`2ad108cd86ac579e.json`) has no `Retry-After` header, so that never happens there.
   - Step 2's log also shows a harness "Missing fixture" error thrown as a value that is not an `Error` object, and the spec reports it as `UNTYPED`, the code the window gives an unclassified error.
   - These failures are the other agent's work in progress.
2. **The budget limits when attempts may start, not the total running time.**
   - The owner's words are "a 90-second total budget per request, retries included; past it the request ends with its last error". The brief adds "a single attempt's own 60-second timeout still applies".
   - So the budget never cuts an attempt short. The last retry can start just before 90 s and run to its own timeout.
   - The true worst case is therefore 90 s plus one request timeout: 150 s at the 60-second default, plus that retry's wait for the host's rate limiter. The `timeoutSeconds` preference can raise the timeout up to 600 s.
   - The measured arXiv case drops from about 150 s to about 95 s.
   - The corrected `docs/07` text states this bound exactly. A hard 90-second end would need in-flight attempts to be aborted, and the request would then end with a timeout error rather than "its last error".
3. **The budget's start is a choice made here.**
   - It starts at the first attempt's hand-off to the transport, not when `request()` is called.
   - Otherwise a request queued behind others on a busy host could use up its budget before it was ever sent, and would lose all its retries.
   - Recorded in the `docs/07` note.
4. **A retry's own wait for the host's rate limiter is not stopped by the budget once that retry has started.** An example is another request's `Retry-After` penalty on the same host. Recorded in the `docs/07` note's worst case.
5. **The `docs/08` §4.6 wireframe disagrees with the new row.** It shows "PubMed: HTTP 429 (rate limited — add an NCBI API key in Preferences)" with an Open Preferences button. The item 205 and item 220 notes and `ERROR_ROWS` give 429 no Preferences action, and this change follows them. The wireframe was not edited.
6. **The other agent's integration run probably ran with one of my mutants in place.**
   - Mutant M8 (the 429 row offers no Retry) was in `searchImportViewModel.ts` from about 18:24:28 to 18:28:54.
   - The other agent's `npm run test:integration` started at 18:28:31, and its Zotero started at 18:28:42. Its build very likely included M8.
   - In that run, a failure of "renders a forced 429…" on "Retry is offered", or any 429 Retry-button assertion, comes from M8. That run should be repeated.
   - The other mutants (M1–M7) were also live between 18:02 and 18:28, but no Zotero test run was seen starting while they were applied.
