# P0-T35: Re-probe cancellation with the abort fired after the first byte

**Date:** 2026-11-25 · **Executor:** Claude Code (agent), batch L (`plan/reports/P7-batchL.md`) · **Commit base:**
26250a9, uncommitted. **State:** `TODO`; only the owner sets `DONE`.

**Caller and constructing file (rule 10).** `scripts/spike-network.ts` is a paste block, so it has no caller in the
plugin. Its entry `mainMidStream` (new, emitted with `--p0-t35`) and `main` both call `midStreamSection`. That
section builds the loopback server (`startLoopbackStream`) and calls legs [14] (`midStreamAbortLeg`) and [15]
(`midStreamClientAbortLeg`). Leg [15] builds its client with `createHttpClient` from `src/core/http/client.ts`.

## Where the card's text is stale (followed the code, recorded here)

1. **The two legs already existed.** Legs [14] and [15] were added on 2026-09-30 (commit 4980899) against Europe PMC,
   a public host, and never run. The brief for this run allows only a loopback server the probe itself starts. So
   the legs now read from one: `startLoopbackStream`, an `nsIServerSocket` bound to 127.0.0.1 only. It reads each
   request to its blank line, then answers `200` with a `Content-Length` body of 196,608 characters, written in 48
   pieces of 4,096 characters, 80 ms apart (about 3.8 s, close to `P0-T16`'s measured 3,897 ms stream). `P0-T17`'s
   legs [11]–[13] are not changed (the diff touches none of their lines), so its numbers stay reproducible.
2. **The client now has a progress hook.** Leg [15] used to abort on a timer set from leg [14]'s first-tick time,
   because the client had no progress hook. Since `P3-T11` it has one, `onBodyText`, so leg [15] now aborts on the
   third delivery: the same event trigger as leg [14], and stronger evidence than a timer.
3. **The client no longer throws `HttpError`.** Since `P1-T02`'s `toHierarchy`, what the client throws for code
   `CANCELLED` is §10.1's `OperationCancelledError`, with no cause; the `HttpError` stays inside the client. So
   "the `HttpError` code the client maps it to" is read from the class. `toHierarchy` builds
   `OperationCancelledError` only from code `CANCELLED`, and a `NETWORK` code would have given a `NetworkError`
   with the `HttpError` as its cause, which the leg checks. `P0-T17`'s leg [12], unchanged, still tests for an
   `HttpError`, so a run of it today would report "unmapped". It was not run here (it needs a provider key).
4. **The card's Do NOT about `src/` holds.** Nothing in `src/` was changed for this card.

## What changed

All in `scripts/spike-network.ts`:

- `startLoopbackStream` and `reportConnection` were added. The server records, for each connection, the request
  line, how many writes were accepted, and the first refused write with its error: the server's own view of
  whether the transfer stopped.
- `midStreamSection` is shared by `main` and the new `mainMidStream`.
- `ProbeEnv` gains `classes` (`Cc`), and its `services` include `tm`, the main thread the server reads on.
- The emitter takes `--p0-t35`, emits the block with `mainMidStream` as its entry, and hands `Cc` in.
- Legs [14] and [15] take the loopback URL.
- Leg [14] names the exception by `instanceof` against all five `Zotero.HTTP` classes, as `P0-T17`'s leg [11]
  does. It answers (b) "readable" only when the read returns text.
- Leg [15] builds its own client over a transport that records what `Zotero.HTTP` itself did.

**Against `P0-T17`'s pre-first-byte result** (`docs/spikes/phase-0.md`, `V-9`): `P0-T17` saw the same exception, 0
ms after the call, 0 ticks in 2,500 ms, and code `CANCELLED`, but with 0 characters received. With 12,288 characters
received, all of that holds. What is new is (b): the body cannot be read back after a cancel.

**Design input, not a failure (the card's Notes).** A Phase 3 job that keeps partial output on cancel must keep the
text as it arrives, not read the response afterwards. `HttpOptions.onBodyText` already hands it over.
