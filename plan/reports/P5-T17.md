## Findings
1. **Decision line 16 does not hold for related runs.** Line 16 says "the job record keeps the seed". `P5-T14`'s decision 1 gives related runs no `JobRecord`, so with the box unticked nothing keeps the seed. No finishing condition asks for it, so this is recorded on the card and is not a new card.
2. **A seed in a group library imports oddly.** `listCollections` lists only the user library's top-level collections, while the items must go to the seed's library. A picked collection's name is therefore resolved, or created, in that group library. This is recorded in decision 2 and not built around.
3. **A cancel can leave a batch unlinked.** A cancel landing between a batch's created items and its linked items throws before the relation pass, so that batch's items stay imported without the link. Recorded in `docs/07` §6.2.
4. **A failed relation pass needs in-memory repair.** The rollback undoes the database, but the cached objects still hold the relations. From `omni.ja`, Zotero recovers only the object whose save failed, so a later save of any other would write what the report says failed. `relateToSeed` therefore reloads `relations` on the seed and items. Only the integration spec can show this works.
5. **`docs/08` §5.1's sample used `saveTx()`.** It is the API documentation's sample, for a call outside a transaction. It is corrected in place by note.
6. **Defect caught by reading, fixed here.** The document's `renderExportControl` treats non-empty `notices` as "a provenance record exists", so a related import would have revealed Export with nothing to export. It now stays hidden by mode, with a unit test and a killed mutant.
7. **Pre-existing, in both windows.** The Import gate reads only the ticked count; `logic.targetNamed` has no runtime caller. With the picker on bare "New collection…" and the prompt dismissed, Import stays on, logs a warning and does nothing visible. Decision 1 makes this rare in the related window. I did not change it, and it blocks no finishing condition.
