## What was built (`src/tts/audioStore.ts`, extended; every `P0-T26` export kept)

- **`silencePcm(ms, format)`.** It returns `round(ms × rate / 1000)` frames times the frame size, as zero bytes.
  `CHUNK_SILENCE_MS` is 250.
- **`wavHeader(dataBytes, format)`.** It returns the 44-byte header. `pcmToWav` now prepends this header, and its
  output and messages are unchanged. Both share `assertPcmFormat`, which keeps `pcmToWav`'s guard and its
  wording.
- **`concatPcm(chunks, options)`.** It joins the chunks into one flat buffer, with silence between them and none
  after the last. It is the reference, and the fallback when the file system cannot append.
- **`PcmChunk { pcm, sampleRateHz }`.** `SynthesizedChunk` (`P6-T11`) can be passed as one.
- **Checks on every chunk, before anything is written:**
  - One rate for the whole file. A chunk at another rate is a `TTSError` with `reason: "sample-rate"`, the same
    reason `synthesizeChunks` uses.
  - A whole number of frames.
  - A chunk that begins with `RIFF` (`docs/04` §2.4) has its sub-chunks walked to `data`. Odd-sized sub-chunks
    are padded, and a `fmt ` whose rate, channel count or bit depth differs from the file's refuses the join (no
    transcoding, §6.4). The strip is logged by chunk index and header length only.
- **`AudioFileSystem.appendFile?(path, bytes)`.** This is `IOUtils.write(path, bytes, { mode: "append" })`. The
  option's name was read in the installed Zotero's `chrome/content/zotero/xpcom/http.js`, which appends with that
  exact call, and `zotero-types` declares `WriteMode` as `"append" | "appendOrCreate" | "create" | "overwrite"`.
  It is optional so that `P0-T26`'s adapter in the integration spec keeps compiling.
- **`AudioStore.writeChunkedWav({ stem, chunks, format?, directory?, logger? })`.** It writes the header for the
  total length, then appends chunk, silence, chunk, and so on. The largest single write is one chunk or one
  silence, so peak memory is the chunks already held plus one silence buffer. Without `appendFile` it builds one
  flat buffer and says so in its documentation. `directory` writes into another folder, which is `P6-T13`'s
  linked-file folder.
- **`AudioStore.pathIn(folder, fileName)`**, used by `P6-T13`.
- **`test/unit/tts/audioStore.test.ts` (new, the file's first unit test), 24 tests.**

**Caller.** `deliverAudio` in `src/pipeline/audioReport/deliver.ts` (`P6-T13`). The store is constructed in
`createZoteroAudioAttachments` (`src/zotero/attachments.ts`), which `P6-T16` wires into
`src/bootstrap/registerPipelines.ts`.

## Decisions taken (each DECIDED 2026-11-16, coordinator, under `plan/00` §6 item 313)

1. **The platform write appends, so there is no flat buffer in Zotero.** The flat path exists only for an adapter
   without `appendFile`.
2. **A stray WAV header is found by walking its sub-chunks**, not by assuming 44 bytes. A `fmt ` that disagrees
   with the file refuses the join.
3. **Every check runs before the first write**, so a bad chunk leaves no partial file.
4. **`assertPcmFormat` is shared** by `pcmToWav`, `wavHeader` and `silencePcm`, and keeps `pcmToWav`'s message.
