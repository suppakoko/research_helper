P3-T12 report: structured output, validation, and the repair path

VERDICT

The card is done at unit level. All of its Done-when lines hold, with two caveats. First, the corpus has no canonical PaperSummary v1 example, so the validator was tested against a hand-built one (Contradiction 1). Second, the four "chat-json-malformed" fixtures are synthetic, because test/fixtures/llm holds only .gitkeep and recorded fixtures belong to P3-T30.

What a schema-constrained call now does:
- It goes through completeJSON and returns a validated object or throws.
- At most three requests are made, in this order: the call, then one repair (docs/12 §18.3's prompt, word for word, at temperature 0), then one full retry of the original request at temperature 0. If the retry's answer is still invalid, the call throws StructuredOutputError(providerId, modelId, message, ctx).
- The limit of three comes from the code's straight-line shape. There is no counter and no loop.
- A truncated answer (finishReason "length") throws LLMError before any repair.
- A refusal throws ContentFilterError with no repair. This covers both a refusal the adapter throws and a "content_filter" stop.
- Any other error from chat() passes through unchanged.
- StructuredOutputError is still outside the transport's retry set. A test checks isRetriedAutomatically for it.

Other points:
- No JSON Schema library was added (NFR-18).
- No new user-visible string was added, so the Korean bundle and KO_PENDING_REVIEW were not touched.
- No live provider call was made and no API key was used. Every key in the tests is built at run time.

CONTRADICTIONS

1. **There is no "canonical PaperSummary v1 example".** docs/06 §6.2 and docs/12 give only the schema. The test therefore uses a hand-built object that is valid against src/prompts/schemas/paper-summary.v1.json, and the test file's header says so.
2. **docs/03 §14.5 against docs/12 §18.3 and this card.**
   - The sketch makes two attempts with an appended correction turn and uses the names 'bad_request' and 'schema_violation'.
   - I followed the card: call, repair, retry at temperature 0, then fail.
   - A truncation is LLMError (messageKey rh-error-llm, "{ $provider } could not complete the request.").
   - The sketch's userMessage "The summary was cut off. Try increasing the output token limit." has no Fluent string and no error class. I added neither, because that would need docs/07 §10.1 and a new string. If the owner wants a dedicated message, that is a question for the owner, not a card from me.
   - Dated note added to docs/03 §14.5.
3. **Step 1 was already done.** P3-T07 to P3-T10 shipped each adapter's native json_schema field. The card lists all four adapter files as "modify", but only OpenRouter's needed a change (step 6). The other three are proved by the four-provider test, not edited.
4. **Where the fallback lives.**
   - docs/07 §4.3 says "Providers without native support get prompt coercion", which puts it in the adapter.
   - The "Deliberately absent" comment in src/llm/openrouter/mapper.ts calls it "the prompt layer's job".
   - docs/12 §18.2 says the fallback is needed for OpenRouter only.
   - I built the shared function withSchemaInPrompt in jsonMode.ts and call it only from the OpenRouter adapter. The mapper comment is now slightly stale; I did not edit it, because the mapper is outside the Files.
   - A generic rule in completeJSON ("supportsJsonSchema === false → coerce") would be wrong. OpenAI's ModelInfo uses false to mean "not known" (P3-T08 Contradiction 3), so every OpenAI call would be coerced.
5. **What the error context carries.**
   - docs/12 §18.3 puts { raw, repaired, errors } in the context, "only when logRequestBodies is on". llm/ reads no preference.
   - So the bodies, redacted through redactText, are included only when the caller passes includeBodies. P3-T25 and P3-T27 should pass getPref("logRequestBodies").
   - By default the context holds the redacted error lines and the output lengths.
6. **The repair is a plain-text call**, per §18.3's llm.text: no responseFormat. On OpenRouter that means the repair carries no require_parameters and may reach a different upstream. Privacy is unaffected: the original's routing hints are copied, and data_collection "deny" is always sent.
7. **The fence stripper is not strictly needed for the malformed fixtures.** The balanced-brace extractor recovers them too. The Done-when line "parses through the fence stripper" holds for tryParseJson as a whole, and the stripper itself is covered only by its own unit test (mutant M6).
8. **{ kind: "json" } with no schema still gets no prompt coercion on OpenAI or OpenRouter.** Nothing sends it, and the card's step 6 is about schema output.
9. **Usage on failure.** When completeJSON throws, the usage of the requests already made is not returned; only a successful result carries the summed usage. The spend on a failed item must be counted by the budget guard (P3-T16).
