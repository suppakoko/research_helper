P3-T09 report: the Anthropic adapter (Messages API)

VERDICT

The card is done at unit level except step 7, which I stopped at on purpose.

What works:
- chat() sends POST /v1/messages with the system prompt at the top level (never as a message) and max_tokens always present. The headers are x-api-key, anthropic-version 2023-06-01, content-type and anthropic-dangerous-direct-browser-access: true.
- Structured output goes through output_config.format. It falls back to one strict tool only when the model list says the model lacks structured outputs.
- countTokens is synchronous and returns estTokens. The exact, free count over POST /v1/messages/count_tokens is a member of the adapter's own type only, not of LLMProvider. It falls back to the heuristic on any failure.
- listModels() follows has_more / last_id across pages and returns the union. max_input_tokens becomes contextWindowTokens and max_tokens becomes maxOutputTokens.
- Usage adds both cache fields to input_tokens.
- The adapter is registered in registerProviders, and a test sends a call through the real router to it.

It follows the P3-T38 pattern exactly:
- every request passes mapErrorResponse calling mapProviderError, timeoutMs: LLM_ATTEMPT_TIMEOUT_MS and the job's cancellation token;
- it contains no retry loop;
- a 2xx answer goes through mapProviderError outside the loop, so a refusal is caught before content is read.

Both showcases were tested through the real createHttpClient with a fake transport:
- the spend-cap 429 ends after exactly one attempt as QuotaExceededError, with no wait;
- the 529 overload is retried as UpstreamServerError marked overloaded, and either recovers or gives up after five attempts.

The key handling:
- the key is read only from the SecretStore and wrapped in Secret;
- expose() is called in exactly one place, and a test checks this;
- logged headers go through loggableHeaders;
- isConfigured() checks the keystore.

No live call was made, no key was read from any file or the environment, and every response body in the tests is hand-built and marked SYNTHETIC. typecheck, lint:check, npx eslint . and npm run test all exit 0.

Step 7 is not done: no api.anthropic.com row, and no change to test/unit/core/hostLimiter.test.ts. The row's request rate depends on the "Open — recommended" line on P3-T07: should LLM rows have no fixed rate, with burst and concurrency taken from the concurrency preference and pacing only from Retry-After? That line is still undecided (review §4 item 5). docs/07 §7.3's LLM/TTS row says the rate comes "from provider prefs", but no such preference exists. plan/04 §0.2 item 10 says to stop at such a step and ask, and plan/README.md §5 rule 4 forbids inventing a rate.

This matters: without a row, createRetryFor gives api.anthropic.com no limiter and no retry policy. So in the product today an Anthropic request makes exactly one attempt. A 529 or an ordinary 429 is not retried, though the spend cap is still correctly not retried. The tests drive the client with LLM_RETRY_BUDGET explicitly, which is exactly what a row carrying retry: LLM_RETRY_BUDGET would give. As of my last check, none of the other three agents had added a row either.

Question for the owner: what request rate should the four LLM rows in HOST_POLICIES carry? Once that is decided, adding mine is one row with retry: LLM_RETRY_BUDGET plus one test.

TESTS, BY NAME (test/unit/llm/anthropic.test.ts, 41 tests)

Block "the Messages request on the wire (docs/03 §3.2–§3.3)":
- puts system at the top level and always sends max_tokens (snapshot)
- sends docs/03 §3.2's four headers, the key only as x-api-key
- sends no system message, no context_window, no sampling field and no trace id
- lifts every system message, in order, into one top-level system
- passes the 3-minute LLM attempt timeout to the transport
- uses a valid base-URL override, joining the path without doubling it

Block "max_tokens is never omitted and never invented":
- refuses a request with no max_tokens and no catalogue entry, before reading the key or sending
- clamps to the catalogue's output cap, and uses the cap when the request has none

Block "structured output (docs/03 §7.2)":
- sends output_config.format, never output_format, and parses the JSON text block
- leaves json undefined for an answer that does not parse, for the repair path
- falls back to one strict tool when the catalogue says the model lacks structured outputs

Block "the Messages answer (docs/03 §3.4, §14.3)":
- joins the text blocks, skips a thinking block, and maps end_turn to stop
- maps max_tokens to length: truncation arrives as HTTP 200
- sums the cache fields: total input is greater than input_tokens
- counts an absent cache field as zero, and an absent input_tokens as unknown
- throws ContentFilterError for an HTTP-200 refusal, and does not read content
- throws LLMError for a 2xx body that is not JSON, without copying the body

Block "the spend-cap 429 and the 529 overload, through the real HTTP client":
- ends a spend-cap 429 after one attempt as QuotaExceededError, with five attempts allowed
- does not retry the spend cap from the exact counter either: one call, then the heuristic
- still retries an ordinary 429 as a RateLimitError, honouring Retry-After
- retries a 529 overload as a retryable UpstreamServerError and recovers
- gives up on a 529 after the five attempts, marked as overload
- keeps the synthetic key out of every error and every log line

Block "the key: keystore only, wrapped, exposed once":
- throws MissingCredentialError and sends nothing when the keystore has no key
- is not configured without a keystore, and follows the keystore's answer
- learns that a key was removed from the keystore when the next call reads it
- logs the request headers only through loggableHeaders
- calls Secret.expose() in exactly one place in the adapter's source

Block "token counts (docs/03 §10.1–§10.2)":
- countTokens is synchronous and is the one heuristic
- lets a stub LLMProvider compile with no exact-count member (a compile-time check that the exact counter is not a key of LLMProvider)
- the private exact counter returns the count_tokens answer
- falls back to the heuristic on a stubbed failure: HTTP 400, a body that is not a count, no key
- still throws OperationCancelledError for a cancelled token

Block "listModels (docs/03 §9.2)":
- follows two pages by last_id and returns the union
- never reads context_window, and leaves out a model without max_input_tokens
- refuses a has_more page that does not advance, instead of looping

Block "validateCredentials":
- answers ok with the models over GET /v1/models, never a completion
- answers a 401 with the error's own message key and status, and a missing key without a request
- counts a 429 as an accepted key

Block "registerProviders registers the adapter, and the router reaches it":
- dispatches a configured anthropic call through the router to POST /v1/messages
- is not configured, and sends nothing, when the build has no keystore

CONTRADICTIONS AND CHOICES

1. Step 7 against plan/04 §0.2 item 10. Covered in the verdict: the row's rate is the undecided P3-T07 open line, and without the row Anthropic requests are neither paced nor retried in the product.

2. Shapes docs/03 does not print. They come from the bundled Anthropic API reference (the claude-api skill), not from docs/03, and are noted in mapper.ts's header:
   - the count_tokens answer, { "input_tokens": N };
   - the model list's data array and the after_id query parameter that carries last_id to the next page;
   - capabilities.structured_outputs.supported, which drives supportsJsonSchema and the strict-tool fallback.
   docs/03 §9.2 and §10.1 could record them. I did not edit docs/03.

3. temperature and topP are never sent. docs/03 §14.2's Anthropic sketch sends neither, and the bundled reference says current Claude models reject sampling parameters with HTTP 400. ChatRequest.temperature and topP are therefore silently ignored for Anthropic, and so are seed and routing. traceId is never sent.

4. max_tokens with no source. ChatRequest.maxOutputTokens is optional in docs/07 §4.3, but Anthropic requires max_tokens. The adapter uses the request's value, clamped to the cap from the model list, or else that cap. With neither, it throws ConfigurationError before reading the key, instead of inventing a number. So the summarizer (P3-T25) must pass maxOutputTokens, or listModels must have run first.

5. Display-name strings were not added. ANTHROPIC_DISPLAY_NAME_KEY is "research-helper-provider-anthropic", but there is no en-US entry, no ko-KR stub and no keys.ts or typings entry. Three reasons:
   - nothing renders displayNameKey yet;
   - those five localisation files are shared by four concurrent agents;
   - docs/08 says provider names are never translated, so the source-name precedent (ko-KR carries the name unchanged, listed in KO_PRESENT) conflicts with the "commented stub plus KO_PENDING_REVIEW" rule.
   The four adapters also disagree on the id: OpenRouter, Anthropic and Gemini use research-helper-provider-<id>, while OpenAI uses research-helper-llm-provider-openai. The coordinator should add all four in one pass, with one naming rule.

6. llm/ imports src/prefs/secrets.ts. docs/07 §2.3 says llm/ imports only core/ and model/, but Secret lives in src/prefs/secrets.ts (P3-T01), and that file's header names the four adapters as its callers. ESLint's layering rule allows the import. The other adapters do the same.

7. validateCredentials is a minimal version; P3-T14 owns it. It is required by the interface, so it does exist:
   - it calls GET /v1/models (docs/09 §2.3: never a completion);
   - success returns ok with the models and the pane's existing id, research-helper-prefs-test-ok, spelled as a literal because llm/ may not import ui/;
   - a 429 counts as ok;
   - any other failure returns the thrown error's own messageKey (rh-error-*) and its HTTP status;
   - it persists nothing.
   No new string was added.

8. isConfigured() is synchronous, but the keystore is not. It answers from the keystore's last answer: refreshKeyPresence (SecretStore.has, which never decrypts) runs at construction and in the background on each isConfigured call, and every key read also updates the answer. Until the first answer arrives, it relies on the registry's anthropic.keyPresent flag. A tested defect was fixed: an explicit refresh had returned the stale answer of a check already in flight. Each refresh now asks the keystore, and only the newest answer is kept.

9. ModelDataPolicy.retention.note is "". It is user-visible text, and the egress-disclosure card (P3-T15) owns it. trainsOnInputByDefault "no" and 30 days come from docs/09 §3.3.

10. LLMCallContext.budget is not enforced here. P3-T06 left open who enforces it; P3-T16 decides.

11. A model-list entry that lacks max_input_tokens or max_tokens is left out of the result and logged at debug level, rather than given guessed numbers.

12. The card's Verify filter finds no tests (see Runs). This is the same defect P3-T05 and P3-T06 reported, plan/00 §6 item 247.
