## What was done

1. **Startup timestamps.** `src/bootstrap/startupTimings.ts` (new) turns `onStartup`'s four `Date.now()` marks into
   `barrierMs` (Zotero's readiness wait), `registerUIMs`, `windowsMs` and `ownMs` (the plugin's own work after the
   barrier). `src/hooks.ts`'s `onStartup` takes the marks and keeps the result on `addon.data.startup`; `src/addon.ts`
   declares the field. Three unit tests in `test/unit/bootstrap/startupTimings.test.ts`.
2. **`test/integration/startupCost.spec.ts`** (new), two tests:
   - the instance it finds kept its timings, and its own work is at most 200 ms;
   - a fresh disable/enable start keeps its timings within 200 ms, and sends no request of its own. Every HTTP
     request in the process is recorded, with a control window of the same length while the plugin is absent.
     `countedStartupHosts` (`test/integration/support/startupRequests.ts`) must come back empty.
3. **`docs/spikes/phase-7-profiling.md`** (new), the owner's procedure:
   - a copy of the library in a separate profile, with no sync (§2.0);
   - `addon.data.startup` read through Run JavaScript (§2.1);
   - five cold starts with the plugin and five without, `Services.startup.getStartupInfo()`, the median difference,
     and a debug-output check for the plugin's `User-Agent` (§2.2);
   - the Gecko profiler at startup, loaded locally in the profiler page, never uploaded (§2.3);
   - memory by `nsIMemoryReporterManager` and `about:memory` (§3), long tasks by the profiler (§4), the XPI (§5);
   - the figures table (§6), with the agent's own figures in §6.1.
