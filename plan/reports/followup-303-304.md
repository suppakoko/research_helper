## FINDINGS
1. **The test's failure was not because Generate was unbound; it was a cross-global check.** The test put its own fake Generate on the host. That fake's error was made in the spec's global, and the plugin's `failureText` tested `instanceof Error`, which fails for such an error. So the banner showed nothing, and only "the redaction mark is shown" failed. This is now measured: an `Error` from the spec is not an instance of the plugin's `Object`.
   - The product fix is `failureText` reading any error-shaped object's message. Errors from Zotero or XPCOM objects have the same shape problem.
   - The test now keeps the host's real `generate` behind a spy. It fakes only the active adapter (`registry.get`) and `secrets.has`, and drives the real cost dialog.
   - Second fix to the test: item B gained an abstract over 250 characters. Through the real binding, an item with no text is skipped with no call (`summary.minAbstractChars` defaults to 250). The fake Generate never noticed this.
   - Every assertion is kept. New assertions: no "don't ask again" box, one model call per run, and zero plugin requests.
2. **The cost dialog opens on every Generate that will make a call.** A run over no collection has no "don't ask again" record, so the routine question always applies. This follows the decided rules, but the owner may find it heavy.
3. **Privacy reading for the owner.** A one-item run uses the global privacy mode (item 278(c)), even when the item sits in a collection that the user set to strict. The per-collection override therefore does not reach the item pane. docs/09 §3.5's per-collection opt-in (for example, manuscripts under review) may need a rule here. The documents do not settle it, and I did not change it.
4. **The key and time-limit questions are answered "stop" in the pane, with nothing more sent.** The time-limit case is close to unreachable with one item. The key case shows the `no-key` line with Retry.
5. **Regenerate on unchanged text is a cache hit.** It makes no call and shows no dialog, and stores the same row again. That is the collection run's rule for re-summarizing; a Regenerate that actually asks the model again would need a rule of its own.
6. **A note saved from the pane for a full-text row names its source "an attachment",** not the attachment's title. The pane does not know the title. The collection run's note-from-stored-row path already does the same.
7. **Concurrency fix.** `createZoteroSummarizeLibrary` used to clear its table of read items on every new read. An item-pane run during a collection run's reading stage would have made that collection run fail.
