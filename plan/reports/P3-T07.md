**P3-T07 report: the OpenRouter adapter, the default provider**

**Verdict.** The card is done at unit level except for step 7. Step 7 (the `openrouter.ai` row in `HOST_POLICIES`) was deliberately not done, because it depends on the card's unresolved "Open — recommended" line about LLM request rates (`plan/04` §0.2 item 10: stop at that step and ask). See Contradiction 1.

The adapter now does the following:
- **Chat.** Sends authenticated chat requests through the shared HTTP client. Every request carries `provider.data_collection: "deny"`. Under `json_schema` it also carries `require_parameters: true`. In strict mode it adds `zdr: true`.
- **Routing lists.** Maps the allow/deny lists onto `only`/`ignore`.
- **Answers.** Normalizes the `docs/03` §5.4 answer, passing `usage.cost` through unrounded.
- **Catalogue.** Parses the public catalogue: prices are `Number(string) * 1e6`, `pricing.overrides[]` is kept, and the structured-output flag is read.
- **Guardrail 404.** Maps it onto `BadRequestError`, naming the cause and both remedies. The match is on status plus `error.code`, never on the sentence.
- **Error hook.** Follows the P3-T38 pattern exactly: `mapErrorResponse` calls `mapProviderError` inside each attempt, `timeoutMs` is `LLM_ATTEMPT_TIMEOUT_MS`, and there is no retry loop.
- **Key.** Read from the keystore, wrapped in `Secret`, with exactly one `.expose()` call (in the header builder). `isConfigured()` answers from the keystore. The catalogue request sends no key.

Checks: typecheck, `lint:check`, `npx eslint .` and `npm run test` all exit 0. Neither Zotero, nor the integration suite, nor `npm run build` was run. No live call was made and no real key was used. Nothing was committed.

**Contradictions**
1. **Step 7 not executed: the `HOST_POLICIES` row for `openrouter.ai`.**
   - The card's open line (LLM rows carry no fixed request rate; burst and concurrency equal the `concurrency` preference; `docs/07` §7.3's "from provider prefs" is replaced) is still "Open — recommended". `plan/00` §6 items 240–259 contain no decision on it, and §0.2 item 10 says to stop at such a step.
   - No number could be written without inventing one: §7.3's rate cell says "from provider prefs", and no such preference exists. The recommendation itself cannot be built as written either, because the `TokenBucket` constructor in `tokenBucket.ts` rejects any `ratePerSecond` that is not positive and finite.
   - Consequence until the owner decides: with no row, `createRetryFor` gives `openrouter.ai` no retry policy. Each request makes one attempt, with no pacing and without `LLM_RETRY_BUDGET`. The spend-cap, guardrail and timeout behaviour is unaffected.
   - The same applies to P3-T08–T10. At the final check, none of the four adapters had added an LLM row.
2. **The guardrail explanation cannot be shown to the user as the card's types stand.**
   - `BadRequestError` is `userFacing = false`, and its `messageKey`, `rh-error-bad-request`, reads "Research Helper sent a request { $database } could not accept", which is the wrong explanation here. The cause and both remedies therefore sit in the developer message and in machine context fields (`cause`, `remedies`, `restrictions`). No new user-visible string was added.
   - `docs/09` §3.4 rule 2 wants a user-facing message. This needs an owner decision: a message id for this case, or a convention for a context-supplied key.
   - Also, "relax the setting in preferences" has only one plugin-side meaning. `data_collection: "deny"` is sent in every mode (`docs/09` §3.5), so the only plugin relaxation is strict → balanced, which drops `zdr`. The message says so.
3. **`displayNameKey` `research-helper-provider-openrouter` has no Fluent message yet.**
   - No surface renders provider display names today.
   - `docs/08` §10.3 forbids translating provider names, which by the source-name precedent means the name appears verbatim in ko-KR and goes on `KO_PRESENT`. That conflicts with this wave's rule: a commented stub on `KO_PENDING_REVIEW`.
   - Suggest one coordinated i18n edit for all four provider names rather than four colliding ones.
4. **The card asks for "recorded" fixtures.** The ones used are hand-built and marked SYNTHETIC; recorded fixtures stay with P3-T30.
5. **The guardrail's structured fields are not documented.**
   - `docs/09` §3.3 marks the sentence Unverified and gives no field shape. The check is therefore HTTP 404 plus OpenRouter's `{ error: { code: 404 } }`, unless a fetched catalogue shows the model does not exist.
   - A genuinely unknown model before any catalogue fetch is therefore reported as a routing refusal.
   - As P3-T38 measured, a redacted body that is no longer valid JSON falls back to the plain `BadRequestError`.
6. **Choices made where the documents are silent.**
   - The catalogue envelope `{ data: [...] }` is not printed in `docs/03` §9.4; both that envelope and a bare array are read.
   - Every catalogue model gets `dataPolicy` "unknown", because §9.4's entry declares no policy. Per-endpoint policy is on the endpoints listing, which no card reads yet.
   - `maxOutputTokens` falls back to the context window when `max_completion_tokens` is absent.
   - `supportsStreaming` and `supportsSystemPrompt` are true for every model.
   - `{ kind: "json" }` sends no `response_format`, because no shape is documented.
   - `servedBy` is undefined, because §5.4 has no field for it and the metadata header's answer shape is unrecorded.
7. **Layering text against the code.** Comments in `registry.ts`, `router.ts` and `baseUrl.ts` say `llm/` may not import `src/prefs/`. But P3-T01 places `Secret` in `src/prefs/secrets.ts` and names the adapters as its callers, and the ESLint layering rules allow the import. The adapter imports `Secret` from there.
8. **`isConfigured()` is synchronous while the keystore is asynchronous.** It answers from the last remembered keystore reply, and "not yet known" counts as configured. `chat()` reads the key itself and throws `MissingCredentialError` before any request when it is missing.
