## COORDINATOR-LEVEL DECISIONS YOU TOOK (each DECIDED 2026-11-02 under item 313, each recorded in the notes above)

1. **Main-bundle lines reach the window as text the host formatted** (a stop's reason, the wall-clock pause, the skipped-dialog cost line). The window's `<linkset>` stays on its own bundle, as `docs/08` §10.1 and `l10n.spec.ts` require.
2. **"Continue" on a job left paused with no run in memory** runs `prepare` again with the run's confirmation, then `execute` in the job's own record.
   - The estimate over-states the stages the cache will serve; it never under-states.
   - A first-job or budget question is asked properly.
   - Declining leaves the job paused and asks again.
   - "Stop" cancels the record, and the cache entries stay.
3. **A shutdown moves no job state.** New outcome `interrupted`. The record stays `running` or `paused` for `recover()`. This applies to window-started runs too.
4. **Closing a window by hand is still a user cancel of a run it started**, as the summarize window does. A resumed run or a paused job is left waiting.
5. **`both` is read as `auto`** until `P4-T21` builds the two-report run.
6. **The final preview is plain text**, the same text the export writes. No Markdown parser is added to the window; the note is the formatted rendering.
7. **"Save as note" is enabled only when** `report.saveNote` is on, the library is editable, and the run's own write did not happen (group answered "no", or the write failed). With the setting off it stays disabled, as the card says.
8. **Copy:** the window script calls `Zotero.Utilities.Internal.copyTextToClipboard`, because `src/` outside `zotero/` may not name `Zotero`.
9. **One window per collection is enforced in the host**, with no second `openDialog`.
10. **The named-group question is asked in place**, after the report is stored and before any note is written.
11. **A cancel, a close or a shutdown releases any question or cost dialog the run waits on**, so no run and no teardown hangs on one. A cost dialog left open after that stays open until the user closes it, and its answer is then ignored.
12. **`TrendReportOutput.noteHtml`** is kept in memory only, for the second note write.
13. **Two extra host-only behaviours:** the spend line reads the job's budget guard, so it shows nothing for an attached resumed run; the host passes the report-language retracted heading to the export now, a one-line part of `P4-T21` that is harmless for English.

## CONTRADICTIONS/FINDINGS

1. **`recover()` never resumes a `paused` record.** It reads `running`, `cancelling` and `interrupted` only. So a job left paused by a guard or by a shutdown stays until its window is opened, and nothing tells the user it exists. Item 324(a) asks for exactly this wait, but no notice points at it.
2. **Same-name `openDialog` may reload a running summarize window.** `openSummarizeWindowCommand` still calls `openDialog` every time. If a second call on a named window reloads the document, a second click cancels a running summarize job. The report window now avoids it. I did not measure this on either window; `docs/08` §6.4's note and the comment on `openReportWindowCommand` state it as fact, so please read both as unverified.
3. **`plan/08` cites `report.enabled` as its precedent for a hidden preference.** The preference no longer exists; only the precedent wording needs care.
4. **Concurrent work in the tree:**
   - A case-sensitive grep finds `/* MUTANT D3h */` in `src/pipeline/shared/requestBudget.ts`, a Phase 5 file (untracked), not mine.
