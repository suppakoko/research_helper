# P7-T39: Closed plugin windows are freed

**Date:** 2026-11-18 · **Executor:** Claude Code (agent), under the coordinator's brief of 2026-11-18 (batch G) ·
**Commit base:** a52225b, uncommitted · **State left:** `TODO`, "built 2026-11-18 (batch G), awaiting the owner's
review". **Owner's answer:** `plan/00` §6 item 403(a), "둘 다 고침". **Caller:** the summarize and report window
commands in `src/bootstrap/registerUI.ts`. **Constructing file:** `src/bootstrap/registerUI.ts`.

## Verdict

**Built; not finished.** The plugin now lets go of a closed summarize window and a closed report window as each
closes. In one development run without the debugger, none of the 20 plugin windows the spec closed stayed alive,
and five reference jobs grew the idle heap by 8.2 MiB. **Not done in the batch:** the three recorded integration runs
and the integration mutants. Zotero stopped starting in the test profile partway through the batch (owner question
`plan/00` §6 item 405(d)).

## What holds a closed window (Do step 1)

Measured 2026-11-18 in the test profile, using weak references to each closed window's document, and a heap
snapshot (`ChromeUtils.saveHeapSnapshot`, dominator tree and shortest paths):

- **With `--jsdebugger`** (the suite's configured `server.devtools: true`), **every** closed chrome window stayed
  alive. That included every plugin window, and also bare control windows that the plugin never touched
  (`about:blank`, and three bare `.xhtml` probe windows). So under the debugger the retention is Gecko's, not the
  plugin's. This explains most of batch F's closed-window share of the growth (+18.6 MiB).
- **Without the debugger**, every closed window was freed except the **last** summarize window and the **last**
  report window:
  - `summarizeState.windows` (a `Set` of window handles) removed a handle only on the next open, when closed ones
    were forgotten;
  - `reportWindowState.windows` (a map from collection to window and session) did the same.
  - The cost dialog had no plugin holder, and it was freed.

## The fix (Do step 2)

All the changes are in `src/bootstrap/registerUI.ts`.

- **`summarizeState.windows`** is now a `Map` from handle to session. `createSummarizeSession` takes an `onClosed`
  callback, and its `closed()` calls it after cancelling a running job. `openSummarizeWindowCommand`'s callback
  deletes the window's entry only while the map still holds that same session, so a window opened again under the
  same name stays held.
- **`createReportWindowSession`** takes an `onClosed` callback too, called at the end of `closed()`.
  `openReportWindowCommand`'s callback deletes the collection's entry only while it still holds that session. It
  moves the session to `reportWindowState.closedSessions`, which the next open clears. Teardown shuts down the open
  sessions and the closed ones, so teardown still waits for a run that a closed report window started (the card's
  Do NOT). **DECIDED 2026-11-18 (coordinator, under item 313; `plan/00` §6 item 404(e)).**
- **`heldCount()`** is on both window commands (`SummarizeWindowCommands`, `ReportWindowCommands`). It returns how
  many windows the plugin still holds, so the spec can wait for the release. **DECIDED 2026-11-18 (coordinator,
  under item 313; item 404(d)).**

## The checks (Do step 3), in `test/integration/workloadMemory.spec.ts`

- **"P7-T39: a closed summarize or report window leaves the plugin's hold as it closes; one opened again stays
  held".** It opens the summarize window twice (the same named window, held once), then a report window, and closes
  both. It then waits until both `heldCount`s are 0, and checks that both `openCount`s are 0. *Passed in the
  development run.*
- **The reference workload** keeps a weak reference to every cost dialog, summarize window and report window it
  closes (`remember`, `closedWindows`).
  - After the closes, it waits until both `heldCount`s are 0.
  - After the growth line, it logs how many of those windows are still alive.
  - It asserts that more than `2 × CONSECUTIVE_JOBS − 1` were tracked.
  - Only when at least one tracked window was freed (`windowsCanBeFreed`), it asserts that none is alive. Under the
    debugger none can be freed. **DECIDED 2026-11-18 (coordinator, under item 313; item 404(h)).**
- **The full-text job** logs whether its summarize window was freed, and the held counts. This is not asserted.
