# Items 230 and 231: timeouts are no longer retried automatically, and the estimate charges no search when none is sent (2026-10-20)

## 1. Verdict

**Done. Every check passed on the final run.** The checks were the type check, both lint commands, the unit and contract tests, and the Zotero integration suite. The integration suite ran twice and passed 165 of 165 both times.

- **Item 230: automatic retries now skip timeouts.**
  - The HTTP client retries only these failures, up to each host's attempt cap in `docs/07` §7.3:
    - a 429 (`RateLimitError`);
    - a 5xx (`UpstreamServerError`);
    - an offline failure (`OfflineError`);
    - a network failure (`NetworkError`, meaning no HTTP response at all).
  - The attempt cap is the total number of tries, counting the first.
  - A `TimeoutError` now surfaces after one attempt. A host that never answers costs one 60-second timeout instead of three.
  - The rule lives in the retry policy, which decides when to try again. The error class's own `retryable` flag still says `true`, so the Search window still offers its Retry button after a timeout. A test confirms this.
  - The dated note in `docs/07` §7.3 was written first. After it, the item-228 note's worst-case wording and the stale "every other row carries `—`" sentence were corrected.
- **Item 231: the estimate now charges zero search requests whenever no search is sent.** `run()` sends no search in exactly three cases:
  - **the input fails validation**: `run()` stops at the Planning stage and sends nothing at all;
  - **the input supplies records**, with or without works: the records are taken as given;
  - **no ticked source can search**: each ticked source is either lookup-only (bioRxiv, medRxiv) or has no adapter. The old formula already gave zero for this case.

  Abstract backfill is the step that fetches missing abstracts in batches. It is still counted on an import of supplied records without works, because backfill runs there. It is not counted on an import of a preview's works, because backfill does not run there.
- **The two stale comments are corrected.** One is the `HOST_POLICIES` header in `hostLimiter.ts`. The other is the reason given in the `UNRENDERABLE_ERROR_ROWS` comment in `searchImportViewModel.ts`. No behaviour changed in either file.

## 6. Contradictions

1. **The `RATE_LIMIT` row's "Retrying in {n}s" still cannot be shown truthfully.** Behaviour was left alone, as instructed. Two reasons hold:
   - **No retry is pending when the error is shown.** The client does retry a 429, but inside the request. The `RateLimitError` that reaches a pipeline result is the one thrown after the last attempt failed, so by the time the Search window shows it, nothing is retrying.
   - **The number of seconds is not available.** The serialized error still drops `retryAfterMs`.

   The comment now gives the first reason in place of the stale one ("container.ts supplies no retryFor"). The second reason was already in the comment. Whether to show the row at all is undecided.
2. **The task named one stale `HOST_POLICIES` sentence, but there was a second.** "Each of those five rows needs its own `retry` budget" was also stale, because the rows were filled on 2026-10-14. That sentence was corrected too.
3. **Skipping timeouts does not bound a slow refusal.** A host that answers every attempt with a 429 or 5xx just before the timeout is still retried to the attempt cap. `P0-T21` measured arXiv 429s taking up to 46 s to fail. Three of those plus arXiv's longest silent waits (3 s + 9 s) is about 150 s. The new §7.3 note says so.
4. **The estimate change goes a little beyond "zero search requests".**
   - **Item count on supplied records without works.** That count is now `records.length`; before, it was `limit × searching sources`. The backfill bound needs a count of works, and the old figure was a search figure on a path that does not search.
   - **Invalid inputs.** These are now estimated at 0 requests and 0 items. `docs/07` §4.5 says validation runs before a job is created, so this branch matters only for a caller that skips validation.
5. **One sentence in the `HOST_POLICIES` header is narrower than it sounds.** The sentence says "the longest a failing request can wait before the job fails is 4 s". That counts only the waits between attempts with no `Retry-After`. Each attempt can itself take up to the 60-second timeout. Not edited: it was not one of the named stale comments.
6. **The 228 report's contradiction 1 still stands.** §7.3's 429 paragraph says the job "fails with a retryable `RateLimitError`" after the cap, but a 5xx ends in `UpstreamServerError`. Not in scope.
