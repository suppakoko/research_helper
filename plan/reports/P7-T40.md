## Verdict

**Built; not finished.** Each acquired paper now holds one compact copy of its text, where it held two two-byte
copies before. In one development run without the debugger, the 500-item full-text job's peak over idle was
167.4 MiB = **175.5 MB**, within 400 MB. **Not done in the batch:**

- the recorded runs, so "with margin across the recorded runs" is **not yet shown**;
- the integration mutants;
- an explanation of about 25 KB a paper.

Zotero stopped starting in the test profile partway through the batch (`plan/00` §6 item 405(d)). The workload was
not lowered: 500 items, about 40 000 characters each, all 500 summarized from the attached text.

## Where the memory went (Do step 1)

Measured 2026-11-18 in the test profile, with the memory reporter's notable-string list (`getReports`, the
`string(length=N, copies=K, …)` paths) at the cost dialog, and heap-snapshot paths:

- **Each paper held two strings of 131,096 bytes**:
  - `source.text`;
  - the body text that the sections' `text` values were cut from. `slice` makes dependent strings, which keep their
    base alive.
- **Why so large.** Zotero's attachment text (`attachmentText`: `getContentsAsync`, then `.trim()`) is a two-byte
  string, and joining the abstract and the body gives the result a power-of-two capacity. So about 40 900
  characters took 128 KiB, twice.
- **Zotero's own copies.** Zotero's indexer keeps each attachment's `bodyText` (81,944 bytes) through its own timers.
  Those copies are made with the items, before the idle reading, so they sit in the baseline and are not the job's.
- At 500 papers, the plugin's two copies are about 500 × 262 KB ≈ 131 MB. That is an estimate from the per-paper
  figure, not a separate measurement.

## The fix (Do step 2)

All the changes are in `src/pipeline/summarize/acquire.ts`.

- **`compactText`** returns an equal string that shares nothing with the strings it was built from:
  `JSON.parse(JSON.stringify(text))`. **DECIDED 2026-11-18 (coordinator, under item 313; `plan/00` §6 item
  404(f)).**
- **`rebaseSections`** cuts each section's `text` again from the final compact `text`, and compacts each heading. A
  section whose `text` is not the slice of its offsets keeps a compacted copy of its own `text`.
- **`acquireSource`** compacts `text`, and the abstract, once they are final. It returns
  `rebaseSections(sections.sections, text)`.
- Nothing in `execute` changed. **DECIDED 2026-11-18 (coordinator, under item 313; item 404(i)).**

## The spec (Do step 3)

The changes are in `test/integration/workloadMemory.spec.ts`.

- **The budgets are in MB.** `MB = 1_000_000`, `BUDGET_REFERENCE_MB = 150`, `BUDGET_FULL_TEXT_MB = 400`.
  `budgetClause` writes "budget 400 MB: N MB, within" or "OVER". The budgets stay logged, not asserted (**item
  404(g)**; the card's Do NOT).
- **"P7-T40: an acquired paper keeps one compact copy of its text"** acquires one item 50 times and holds every
  result. It measures the `explicit/…/strings` total before and after, and asserts that the strings per paper are
  below **two bytes a character**, that is, below one two-byte copy.
  - The first bound, 1.5 bytes a character, **failed** in the development run: 66,042 bytes for 40,928 characters.
  - It was set to 2 bytes. **DECIDED 2026-11-18 (coordinator, under item 313; item 404(k)).**
  - Before the fix a paper held about 6.4 bytes a character, so the test still fails on the old code (expected; not
    run, see Mutation testing).

## Unit tests

`test/unit/pipeline/acquire.test.ts` has a new describe, "compactText and rebaseSections (P7-T40)". It checks:

- identity over the empty string, ASCII, Hangul and CJK, lone surrogates, control characters, and 50 000 characters;
- that a re-cut section's fields are equal while the objects are new;
- that a section whose `text` does not match its offsets keeps its own `text`;
- an empty list;
- an `acquireSource` invariant: every section's `text` equals `text.slice(start, end)`.

25 tests in the file pass.

## The unexplained 25 KB a paper

One byte a character for 40,928 ASCII characters is about 41 KB. The development run measured about 66 KB a paper.

- A probe that broke this down was written: the whole result, then only the text, the sections, the abstract, and a
  second round trip, each with the notable-string sizes. It never ran, because Zotero no longer started (item
  405(d)).
- So **the other 25 KB is not explained**. The candidates (the sections' heading copies, the abstract's copy, a
  capacity rounding on the JSON result) are guesses.
