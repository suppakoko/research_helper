# Items 227 and 229 (part): late translator copies go to the trash, PMID batch deadline, suite-wide translator stub

## 1. Verdict

**All three decisions are done. Every check passed on the final tree, and no live request was sent (0).**

- **Item 227, the late copy.** A translator lookup can miss its deadline. "Translator lookup" means Strategy B: importing a record through Zotero's own identifier lookup, `Zotero.Translate.Search`. It sits behind the `useTranslators` preference, which ships off. When such a lookup misses its deadline, the record is hand-mapped. Hand-mapping (Strategy A) builds the item from the search result's own fields. The abandoned lookup still runs, and when it finishes, Zotero saves its item into the collection anyway.
  - Now, once the abandoned lookup finishes, the items it saved are moved to the Zotero trash. The trash is reversible, and nothing is erased.
  - A warn-level log line records the counts only.
  - The items are identified by the lookup's own `Translate` object, which is the most certain of the three candidate methods. The owner's "stop and report" condition (no certain way) therefore does not apply.
- **Item 227, the PMID batch deadline.** A batch of PMIDs (PubMed numbers) looked up together gets 30 s plus 1 s per PMID, capped at 5 minutes. A lookup for one record keeps 30 s. The rule went into `docs/07` §12.1 before any code changed.
- **Item 229, the suite-wide stub.** Every integration spec now runs against a stub `Zotero.Translate.Search` that refuses to construct. A spec that reaches the real translators without its own fake now fails the run instead of sending requests.
  - This was checked with a mutant (a deliberate defect inserted to prove a test catches it) that switches Strategy B on for every import in the suite. 100 lookups were refused, the run stopped with a failure, and no translator ran.
- **One addition beyond the owner's wording.** A lookup whose deadline passes before its `translate()` call has started now never starts that call, so it saves nothing at all. Section 6, item 4 explains this.
- The final `grep -rn MUTANT src test addon typings scripts` finds nothing (grep exit 1).

## 6. Contradictions

1. **The 5-minute cap never binds at the shipped batch size.** 30 + 200 = 230 s, and the cap needs more than 270 PMIDs. `PMID_LOOKUP_BATCH_SIZE` is 200, so only the direct test of `pmidBatchDeadlineMs` can detect the cap's removal.
2. **"A single-record lookup keeps its 30 s" against a batch of one PMID.** A lone PMID still travels as a one-member batch. The code treats any lookup covering one record as single-record, so it gets 30 s, not 31 s. A batch of 2 gets 32 s. `docs/07` §12.1 states this reading.
3. **No existing item-write helper in `src/zotero/` trashes anything.** `moveItemsToTrash` is new.
   - It lives in `translatorImport.ts`, because `importer.ts` imports that file, and the reverse import would be circular.
   - `collectionOps.ts` was outside scope.
   - It follows the importer's transaction rule: database work only, inside `Zotero.DB.executeTransaction`.
4. **The early stop is an addition.** The owner decided "trash when it settles". The code also skips `translate()` when the deadline has already passed, so such a lookup has nothing to trash. This is consistent with the decision but goes beyond its wording.
5. **A shared `afterEach` failure stops the whole run.** Mocha 12, the test runner, skips every remaining test when a hook registered outside any `describe` fails. One incident therefore ends the run rather than failing only one test. This is loud, as asked, but later tests do not run.
6. **The setup has to be a spec file.** The scaffold (`zotero-plugin-scaffold` 0.9.2) only bundles `*.spec` and `*.test` files and has no in-Zotero setup hook. `_suite-guards.spec.ts` sorts first and installs the stub when its script loads.
   - In the scaffold's watch mode, only the files touched by a change are reloaded, so the guard file may not load. The project's runs use `--exit-on-finish`, which loads every file.
7. **Test cleanup still erases its own fixtures.** `after()` calls `Zotero.Items.erase` on items the spec created, including the trashed late copies, as the suite always has. The product code only ever trashes.
