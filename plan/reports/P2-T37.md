## Step 2 measurement (in Zotero 10.0.3)
The key alone finds the item. The measurement:
- A PMCID-only work was written through `toZoteroMapping` and a strict `fromJSON` save.
- The saved item's `extra` field read `rh-work-key: hash:d3af4f6b…\nrh-sources: pubmed`.
- `findExisting({}, work.workKey)` returned `{"itemID":3517,"matchedOn":"workKey"}`.
- `findExisting(work.ids)` with no key returned nothing. That is the defect.

The writer always keeps `rh-work-key` as the first `extra` line, and a re-run computes the same hash from the same title, year and first author. So no new lookup was needed.

Side fact: on 10.0.3 the PMCID is stored in a native `PMCID` field (the log shows `PMCID field="PMC990037001"`). A PMCID lookup would therefore be possible, but it was not needed.

## Contradictions
1. **The Done-when line "the two new tests fail with the call sites reverted" cannot hold for the `libraryIndex.spec.ts` test.** That test calls `findExisting` directly and goes through neither call site. It is caught by MC, the index-side mutant, instead. The window call site (MB) is covered only by P2-T16 step 6. No dedicated test reaches `isExisting`.
2. **The card says `isExisting` should "pass the work's key", but the window port gets a `SourceRecord`, which has no key.** I derived the key from the single record. For a row whose merged group has two or more records and no identifier, that key can differ from the merged work's key. Fixing that would need the view model (`toWindowRecords` in `src/ui/viewModels/searchImportViewModel.ts`) to pass the merged work, and that file is outside this card.
3. **Stale comment in `registerUI.ts`.** The doc comment on the module-level `libraryIndex` variable still cites `findExisting` by line number ("`libraryIndex.ts:157` … `:322`"). It also names `src/bootstrap/registerPipelines.ts` as a caller, but no call to `findExisting` exists there. I left it alone as out of scope.
