FINDINGS
1. **The sub-batch count can under-state (it predates this change; owner's call).** `planSynthesis` reserves the larger of one call per theme and the calls needed to carry every summary. A split theme's last call is only partly filled, so several themes each just over one call's room can need up to one more call per such theme, plus its merge. Example on the estimate's own worst case (1 600-token summaries with the 1.15 headroom): 150 papers at K = 9, in six themes of 22 and three of 6, needs 15 theme calls and 6 merges against the 10 reserved. `withBudget` still catches this at dispatch. It is recorded in the docs/07 §4.5 note and was not fixed (out of scope).
2. **Reading of the merge cap.** Item (b) does need the +1 for merges, but only from 2K + 2 needed calls (522 papers at K = 12), where `Other` too could split. Below that, the extra theme can only lower the merge count, so the plan keeps the larger count for each kind, and at 400 papers the reservation is unchanged (20 theme calls, 8 merges). Tests pin 521 papers → 12 merges, 522 → 13, and K passed as 12 → 12.
3. **The cost dialog still says "up to K themes"** (`SynthesisPlan.themes` is still K, the model's maximum). With `Other`, a run can end with K + 1. The dialog line was left unchanged.
4. **Preference timing.** The menu reads `report.enabled` only when it is registered, at startup or enable. The opener reads it on every call. So turning it on needs a disable/enable cycle or a restart before the entry appears, which is what the new menus test does: two plugin cycles. The key name `report.enabled` is my proposal for the owner to confirm. It is not ⚠-marked in §8.5.
5. **`APP_REGISTRATIONS` keeps its name.** Its collection entry is now an arrow function that builds the options when it is registered, so the reference in `toolsMenu.ts`'s comment still holds.
