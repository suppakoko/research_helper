PAUSE REASON CHOSEN, AND WHY
A new reason, "wall-clock-budget", rather than reusing an existing one. A pause notice, and after a restart the stored row itself, has only JobRecord.pauseReason to decide which question to show. The two candidates already mean other questions:
- "awaiting-confirmation" is the confirm guard's cost question over an estimate (item 250).
- "budget-stop" is §12.3's money BudgetStop and shows the amount spent (isBudgetStop).
Reusing either would make the surface unable to tell "N of M done — continue the rest?" from those questions. The pause_reason column has no CHECK constraint, so no migration was needed, and fromJobRow accepts the reason through PAUSE_REASONS.

THE TWO ENGLISH STRINGS, VERBATIM

rh-error-output-truncated = The summary was cut off by the output length limit of { $model }.

research-helper-job-wall-clock-budget =
    { $minutes ->
        [one] Paused after 1 minute of work. { $done } of { $total } done — continue the rest?
       *[other] Paused after { $minutes } minutes of work. { $done } of { $total } done — continue the rest?
    }

The arguments:
- $model: the model ID, untranslated.
- $minutes: the budget in minutes (30), used as a plural selector.
- $total: the job's item count.
- $done: the items settled so far (summarized now, already cached, or failed), so a yes runs exactly $total − $done.

CONTRADICTIONS AND CHOICES MADE (FOR THE OWNER OR COORDINATOR)
1. "budget-elapsed" is removed from PooledRunStop and from docs/07 §7.5's type block, because the run no longer ends at the budget. P3-T17's test that asserted it was replaced.
2. A yes resets the budget to a fresh 30 minutes; only the budget's own pause resets it. This is a choice made here; the decision text does not say it.
3. The budget is checked after the done-probe, so a job whose remaining items are all cache hits finishes without asking. The check is still before the wait for a pool permit, so time spent waiting behind other jobs counts as running time. An item can therefore start shortly after the limit if its permit wait began before it.
4. The question's $minutes argument and its leading sentence ("Paused after 30 minutes of work.") go beyond the owner's wording "N of M done — continue the rest?". They were added so the user knows why the job paused. The wording is open to review.
5. The truncation message names no remedy. docs/07 §10.2 asks for "one actionable next step", but nothing decides where maxOutputTokens comes from (P3-T25 sets it), so "choose a model with a larger limit" could be false. The §10.2 row says "Item counted as failed; the job continues."
6. A Gemini interaction with status "budget_exceeded" (readInteraction in src/llm/gemini/mapper.ts) is refused as a plain LLMError, not as a finishReason "length". It was left unchanged, as not proven to be a truncation.
7. A truncated repair answer, the second request in completeJSON, is still judged as malformed JSON rather than as a truncation. This is P3-T12's shape, unchanged.
8. docs/07 §12.3's state diagram ("Paused : user pause / offline / circuit breaker") was not edited, to keep edits in the shared file to what was asked. It does not yet name the wall-clock budget.
9. After a restart, a job paused with "wall-clock-budget" stays paused (recover() leaves paused jobs alone), and its in-memory run is gone. Continuing it then needs P3-T29 to re-run from the checkpoint. Nothing here does that.
10. The spend-ceiling pause the decision mirrors (P3-T16) is not built yet, so the two pauses share a shape on paper but not yet in code.
