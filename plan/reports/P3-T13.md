CONTRADICTIONS AND CHOICES
1. The card's Do NOT says "do not hardcode a model ID or price outside addon/prefs.js's seed defaults", but step 3 asks for a bundled fallback list, and docs/03 §9 asks for "a small bundled default list". Following the coordinator's instruction, the bundled list is the docs/03 §12.1 table, held in one place (DOCUMENTED_PRICE_TABLE), dated, used only when every fetch fails, and tied to the document by a test. Its 13 model IDs and prices are the only ones in the code.
2. Step 4's "user-editable override table" has no store. docs/07 §8.5 has no row for it, and only P3-T32 may add one. Built: the UserPriceOverride type, findUserPriceOverride, applyUserPriceOverride, and the catalogue's userPriceOverrides dependency (defaults to none). Not built: persistence and any editing surface. Needed: a preference row (for example a JSON string, model to price and date, written by the pane) declared in docs/07 §8.5 first, then added by P3-T32; or a decision that the table lives in the plugin database instead. A user row replaces every other price for its model, tiers included.
3. The card and docs/03 §10.2 say "the estimated-to-actual input ratio", but a factor that corrects the estimate by multiplication is actual ÷ estimated. That is what is stored; it is measured against the raw heuristic and summed per job. Recorded in docs/03 §10.2 with the blend of 0.5, a number no document gave, for the owner to confirm.
4. Tier boundary. docs/03 §9.4 ("above 272,000 prompt tokens") and the card ("above its min_prompt_tokens") say strictly above; costOf follows that. The doc comment on OpenRouterPriceOverride.minPromptTokens in P3-T07's src/llm/openrouter/catalogue.ts says "at or above". That file was not edited. The difference is one token at the threshold, and whether OpenRouter's bound is inclusive is unverified.
5. Headroom. docs/03 §10.2 says 20 %; docs/06 §5.1 (D-06-5) says 1.15× plus maxOutputTokens + 800. estTokens applies neither; the budget step (P3-T16) does. The note in docs/03 §10.2 says the code follows docs/06 here, as P3-T06 already did.
6. Callers (plan/README.md §5 rule 10). The card names P3-T14 and P3-T16 as the catalogue's callers, and neither exists yet, so createModelCatalogue is constructed nowhere. It needs the graph's cache, the registry and the OpenRouter adapter's listCatalogue, so it belongs beside registerProviders or in installServices (both shared, both outside this card's Files). The calibration recorder's caller (record after each call, flush once at job end) is the job runner, P3-T17's pool or P3-T25's summarizer; neither card's Files says so yet.
7. The four adapters' countTokens still call estTokens(text) without a model ID, so they stay uncalibrated. The adapters are shared with P3-T12 and were not edited. The estimator (P3-T16) should call estTokens(text, modelId) directly.
8. The Anthropic adapter fills its own model cache only from its own listModels. When the catalogue is served from the 24 h cache, the adapter's getModel stays empty, so item 261(e) still holds: the summarizer must pass maxOutputTokens on every Anthropic request.
9. P3-T07's catalogue parser does not read pricing.input_cache_read, so a live price has no cached-input figure, and cached tokens are billed at the input price (an over-quote, never an under-quote).
10. In the bundled list, the OpenRouter slugs carry the native prices. docs/03 §12.1 says OpenRouter does not mark up and that gpt-5.6-sol is cheaper there, so this can only over-quote.
11. GPT-6 Astra's long-context tier (docs/03 §9.4 and §12.3 item 2) is not in §12.1's table, so the bundled list does not carry it. A live catalogue does.
12. docs/07 §4.1 has no namespace for a model catalogue. The lists are cached in "source-response" (raw upstream payloads) with an explicit 24 h time-to-live and a provider:<id> tag. docs/03 §9 says "cache in prefs"; the card's Cache layer was followed.
13. The promotion's end is taken as 2027-01-01 00:00 UTC; §12.1 names no time zone.
