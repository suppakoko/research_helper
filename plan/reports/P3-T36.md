The gate's signature and the shape of its mark
```ts
export function redactRecord<T>(record: T, options?: RedactRecordOptions): RedactedRecord<T>
interface RedactRecordOptions { readonly verbatimKeys?: readonly string[] }
interface RedactedRecord<T> { readonly record: T; readonly mark: RedactionMark }
interface RedactionMark {
  readonly partlyRedacted: boolean;   // true when anything was rewritten or removed
  readonly redactedStrings: number;   // strings redactText changed: values and property names
  readonly droppedFields: number;     // fields removed under the omitSecretFields rule
}
```
- The mark is counts, not paths. A path would be built from the record's own property names, which could carry a key.
- The gate is idempotent: a second pass returns an equal record and a mark with partlyRedacted false. The doc comment therefore tells callers to keep the mark from the pass that produced the stored value.
- The input record is never modified.

Contradictions
1. Card step 1 against usage records. Step 1 says to drop "every field whose name matches KEYISH_FIELD (omitSecretFields)". KEYISH_FIELD matches "token", so done literally it would delete inputTokens and outputTokens from every usage record, which the job record's usage_json and StoredSummary.usage both hold, and contextWindowTokens and maxOutputTokens from every ModelInfo in CredentialCheckResult.models. The gate therefore applies omitSecretFields only to fields whose value can carry text: a string, an array or an object. A key-named number, boolean or null is kept. This is a P3-T36 choice for the owner to confirm.
2. Running over every stored record against identifiers. A SHA-256 contentHash is 64 hexadecimal characters, and a "hash:" work key carries 40. KEY_PATTERNS replaces both, so with no exception every StoredSummary row would lose its identity and carry the mark. P3-T25 step 6 persists contentHash. The gate therefore takes verbatimKeys: a string, or an array of strings, under a listed name is copied unchanged, as redactMergeDecision already does for workKey. A key-named field is still removed even when listed. This is a P3-T36 choice for the owner to confirm. It is an exemption, not a pattern, but it is a hole if a caller lists a field that holds user or model text; the doc comment forbids that.
3. Card "Verify with". The command `npm run test:unit -- "core/provenance|errors"` exits 1 with "No test files found", because Vitest 5 treats the filter as a substring. I added a corrected command to the card.
4. docs/07 §5.2: no StoredSummary or JobRecord member holds the mark yet. My note gives that member to P3-T25 (StoredSummary) and P3-T34 (JobRecord) rather than declaring it here.
5. A key-shaped property name is redacted. When two property names redact to the same text, the later field wins. This is documented on redactRecord.
