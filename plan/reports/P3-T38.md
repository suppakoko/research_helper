**P3-T38 report: Keep an LLM 429's body; never retry a parse failure**

**Verdict.** The card is done at unit level. A request can now carry its own error reader, `mapErrorResponse`. For an answer of status 400 or above, the shared HTTP client asks that reader inside the attempt, before it picks an error class, and throws whatever the reader returns. So a synthetic Anthropic spend-cap 429 reaches the caller as `QuotaExceededError` after exactly one transport call, even with five attempts allowed. An ordinary Anthropic 429 is still retried as a `RateLimitError`. The reader only ever receives the body after `redactText`, so it cannot attach an unredacted body to anything it builds. Literature hosts pass no reader, so their behaviour is unchanged: same classes, a body only on `BadRequestError`, retries under each row's budget, and `penalize` from `Retry-After`. Every existing test in `http-client.test.ts` passes unmodified. Two existing tests in `backoff.test.ts` had their loops moved into helpers, as step 5 requires (Contradiction 1). The retry loop no longer re-sends a request whose answer failed to parse (`StructuredOutputError`), and that class keeps `retryable: true`. Typecheck, both lint commands and `npm run test` pass. Neither Zotero nor the integration suite was run, as instructed.

**Design chosen: Option A, a hook passed with each request, and why.**
- **Where it lives.** The hook is a new optional member, `HttpOptions.mapErrorResponse`, with the type `ErrorResponseMapper = (response: HttpResponse, nowEpochMs: number) => ResearchHelperError | undefined`. It is not on `HttpClientDeps`, and it is not on a `HOST_POLICIES` row.
- **Why per request.** `mapProviderError` needs the request's model id, which only the adapter knows. A row in `src/core/` could not import that function anyway, because of the layering rule.
- **Why not Option B.** B is not simpler, for three reasons:
  1. B attaches a body to every 429. That changes a literature host's 429, which must stay bodiless, unless a per-host or per-request flag is added, and that flag is a hook in all but name.
  2. B still needs a separate way to stop the retry. `withRetry` decides inside the loop on a `RateLimitError` that is `retryable: true`, so without one a spend cap is sent four more times.
  3. Under B the adapter has to re-map the error after the loop has finished.

  A needs one optional member, and it does not touch `errors.ts`, `RateLimitError`'s constructor or `installServices`.
- **Where it sits in the attempt.** The hook runs inside `classify`:
  - after `adoptLimits`, and after a 429 or 503 `Retry-After` has `penalize`d the host, so the host is parked whatever class the answer becomes;
  - before any status branch;
  - never for a status below 400.
- **What it receives.** The response, with only `body` replaced by `redactText(body)`, plus the client's injected `clock.now()`.
- **Still one of each.** There is one retry loop (`withRetry`), one `Retry-After` parser (the hook's `mapProviderError` calls the same `parseRetryAfter`) and one redactor.
- **Measured limit** (tsx script, scratchpad). When the redactor's 40-character catch-all matches straight after a JSON escape such as `\n`, the redacted body is no longer valid JSON. `mapProviderError` then maps by status alone, so such a spend cap is retried as a rate limit. That is today's behaviour, not a leak. It is recorded in the `docs/07` note.
