**Retry and timeout numbers as shipped**
- **Budget:** `LLM_RETRY_BUDGET` = base 1000 ms, cap 60 000 ms, 5 attempts. The 5 includes the first attempt, so it allows four retries. The object is frozen.
- **Waits:** through `withRetry` the waits are 1 s, then at most 3 s, 9 s and 27 s: 40 s at the longest and 4 s at the shortest. The 60 s cap never applies at five attempts.
- **Server delay:** a sent `Retry-After` is the wait itself and is not capped.
- **Attempt timeout:** `LLM_ATTEMPT_TIMEOUT_MS` = 180 000 ms. Each adapter must pass it as the request's `timeoutMs`. Literature hosts keep `timeoutSeconds`, 60 s by default.
- **Timeouts:** never retried automatically (item 230), so a silent LLM host costs one 3-minute attempt.
- **How the 90 s budget meets a 3-minute attempt.** `REQUEST_BUDGET_MS` = 90 000 ms is unchanged. It only decides whether a retry may start and never cuts an attempt short. So:
  - An LLM attempt that fails after 90 s or more is never retried. A long generation that ends in a server error therefore gets one attempt.
  - All five attempts happen only when the failures are quick. Five 1-second failures plus the longest waits end at about 45 s; a test measures the attempt starts at 0, 1, 4, 13 and 40 s.
  - The worst case is a retry started just inside 90 s that then runs its full 3 minutes: about 270 s after the first attempt reached the network, plus that retry's wait for the host's rate-limit queue.
- **Batch budget:** not built here; it stays with `P3-T17`.
- **Preference:** none is needed for the decision. A preference such as `llm.timeoutSeconds` would only be worth adding if users on slow models start hitting the 3-minute limit, and only `P3-T32` may add it.

**Contradictions**
1. **The client hides the spend cap.** `classify` in `src/core/http/client.ts` throws a bodiless `RateLimitError` for every 429, inside the retry loop. An Anthropic spend-cap 429 is therefore retried until the attempt cap or the 90 s budget stops it, and arrives at the adapter unrecognisable. OpenRouter's 402 is safe, because it arrives as a `BadRequestError` with its redacted body attached. Fixing this needs a change to `client.ts`, for example a per-host hook that sees the response before it is classified, or the body attached to 429s. That belongs to `P3-T07`–`P3-T10` or a new card. It is recorded in the new `docs/07` §7.3 note.
2. **`StructuredOutputError` would be retried by the transport loop.** `isRetriedAutomatically` in `src/core/http/retry.ts` returns true for it, because the class is marked `retryable: true`. `docs/03` §14.1 says it is deliberately outside the transport retry set. Today this does no harm: the client never throws it, and `mapProviderError` never returns it (tested). But an adapter that parses the answer inside `withRetry` would re-send the same request. `retry.ts` is not in this card's Files.
3. **Stale header in `src/core/rateLimit/backoff.ts`.** It still says `docs/03` §11.6's full jitter will be added to that file by "P3-T05 step 7". The owner chose one jitter shape, so the sentence is now wrong. The file is not in the card's Files and was left unchanged.
4. **Stale sentence in `docs/07` §8.5.** It explains `timeoutSeconds` = 60 as doubling Zotero's default "because LLM calls are long". LLM attempts now use the 180 s constant. §8.5 belongs to P3-T32, so I did not edit it.
5. **The card's Verify command finds no tests.** Vitest filters match plain substrings, not `|` alternatives, so `"errorMap|hostLimiter|keys"` matches no file and exits 1. Separate arguments work.
6. **A file outside the card's Files had to change.** `typings/i10n.d.ts` is generated from the bundles, and the new ids would not typecheck without it. I inserted the four lines by hand in sorted order instead of running `npx zotero-plugin build`, to avoid writing into `.scaffold/build` while P3-T32's agent might be running tests there. The coordinator's landing build should regenerate it with no difference.
7. **Signature deviation.** The card names `mapProviderError(providerId, modelId, status, headers, body)`. The shipped function has a sixth parameter, `nowEpochMs`, because `parseRetryAfter` needs the caller's `clock.now()` to read the date form of `Retry-After`, and reading `Date.now()` directly would bypass the injected clock.
8. **Adapter rows will fail an existing test.** `test/unit/core/backoff.test.ts` requires every `HOST_POLICIES` row to match a §7.3 row by its backticked host name. LLM rows added by `P3-T07`–`P3-T10` (for example `api.anthropic.com`) will fail that test unless §7.3 gets one row per LLM host or the test learns about the shared LLM/TTS row.
9. **Gemini gaps in the corpus.** `docs/03` records no spend-cap shape for Gemini separate from `RESOURCE_EXHAUSTED`, so a Gemini 429 maps to `RateLimitError`. `docs/03` also does not record what the Interactions API returns when safety blocks an answer. Only the older `generateContent` fields (`finishReason`, `promptFeedback.blockReason`) are detected; `P3-T10` must add the Interactions shape.
10. **My wording for three strings needs the owner's review.** `docs/08` §8.3 has no rows for LLM errors. The `rh-error-content-filter` text is quoted from `docs/07` §10.2; the other three English strings are my own.
11. **A partly stale comment in `hostLimiter.ts`.** The header comment still says LLM hosts "are driven from provider prefs rather than from a static row". That remains true for request rates but no longer for retries. Left unchanged.
