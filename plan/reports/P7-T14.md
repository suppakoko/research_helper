## What is real, and what is a double

- **Real:**
  - the plugin instance and its service graph, every window and dialog, the job queue and the plugin database;
  - the three pipelines;
  - the **OpenRouter adapter**, which reads the key, builds the `Authorization` header, logs its "openrouter
    request" line and parses the answer;
  - the **Gemini text-to-speech client**, which reads the key and sends it in `x-goog-api-key`;
  - the HTTP client and its log lines, the redacting logger and the log ring.
- **Planted keys (coordinator decision, under item 313; the brief: "recorded test fixtures only").**
  `graph.secrets.get` and `.has` are patched **in memory**. They answer one synthetic key per secret id, each of its
  provider's shape and drawn at random for each run:
  - `llm.openrouter` `sk-or-v1-` + 64 hexadecimal; `llm.openai` `sk-proj-` + 48; `llm.anthropic` `sk-ant-api03-`
    + 80;
  - `llm.gemini` and `tts.gemini` `AIza` + 35;
  - `source.ncbi` 36 hexadecimal; `source.semanticscholar` 40.

  The keystore is never read or written. No real key exists anywhere in the run.
- **`Zotero.HTTP.request` is doubled** for the plugin's requests, routed by `isLiveRequest`
  (`test/integration/support/liveRequestGuard.ts`). Nothing leaves the machine:
  - the OpenRouter chat answers are built by the spec from each request (summaries, then the report's sections);
  - the audio script is the committed `test/fixtures/llm/openrouter/audio-script-en.json`;
  - each speech chunk is `test/fixtures/tts/gemini/tts-en-short.json`;
  - the Gemini model list is `test/fixtures/tts/gemini/models-list.json`.

  Every one of these fixtures says `"synthetic": true`. They are stand-ins, not recordings (`plan/09` `P6-T03`), and
  the spec logs that it read them. The double refused nothing (asserted).
- **The model metadata** (`getModel`, `listModels`) is the mock every model-driven spec uses. A streamed call is
  answered through the adapter's own non-streamed `chat`, so it too goes through the real adapter and client.
- **The spec checks that the keys were really sent.** The planted OpenRouter key arrived as `Bearer <key>` in
  `Authorization`, and the planted Gemini key arrived in `x-goog-api-key`. This shows the search ran over output of
  code that held the key.

## Decisions (coordinator, under item 313)

1. **Recorded fixtures, not a keyed run** (`plan/10` §0.4 line 17, and the brief). The keys are planted in memory,
   so the adapters that read keys run for real and nothing is spent.
2. **Only credential headers are searched for as header values.** `Do` step 2 says "the header names' values". The
   first development runs searched for every header's value, and found the OpenRouter attribution headers
   (`HTTP-Referer`, `X-Title`, `X-OpenRouter-Title`) in the "openrouter request" debug line. Their values are the
   project's page and the tool's name (`docs/03`'s OpenRouter headers; `src/llm/openrouter/mapper.ts`), not secrets.
   `loggableHeaders` (`src/core/errors.ts`) is written to keep a non-credential header, passed through `redact`. The
   `User-Agent` holds the maintainer contact, which the brief allows only there, and `Content-Type` is not a secret
   either. The spec logs the names it did not search: `Content-Type`, `HTTP-Referer`, `User-Agent`,
   `X-OpenRouter-Title`, `X-Title`.
3. **The report window is closed and reopened before the audio job.** The audio section reads the latest stored
   report when its window opens, as a user would see it after a restart.
4. **`tts.targetMinutes` is 1 for the audio job.** The derived length gave a sound file over the 10 MiB import
   bound, which sends the job to the linked-folder mode and its folder picker. The linked folder is the user's own
   path, which no test should choose.

## Findings

None that blocks a finishing condition.

1. **The logged `Authorization` header reads `[redacted:13]`, whatever the key.** Recorded in the "openrouter
   request" debug line. `loggableHeaders` (`src/core/errors.ts`) turns the value into `[redacted:80]`: "Bearer " and
   the 73-character key. The logger's key-based rule (`redactValue` in `src/core/logger.ts`) then redacts the same
   field again by its name, and reports the length of the 13-character string `[redacted:80]`. No value leaks. Only
   the length hint is lost. **Not a card under rule 9:** it blocks no finishing condition.
2. **`Verify with` cannot run as written.** `zotero-plugin test` 0.9.2 takes no spec filter (as `P7-T18` recorded),
   so `npm run test:integration -- redactionAudit` runs the whole suite. During development the spec ran alone,
   behind a temporary `.only` that was removed before the three runs.
3. **Not captured: `Zotero.HTTP.request`'s own debug lines**, because its request is doubled. Instead, the spec
   searches every URL the double received, which is where `Zotero.HTTP` would print a key.
