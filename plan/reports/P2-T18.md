# P2-T18 report: translator import path behind `useTranslators`

## 1. Verdict

**Built and tested, with three parts stopped and reported.** The card's `State` and `Findings` are untouched, and no git command that writes was run.

- **Built:** Strategy B, meaning import through Zotero's own identifier lookup (`Zotero.Translate.Search`), switched on by the `useTranslators` preference. It includes the following:
  - the preference is read once per run;
  - the off path is unchanged;
  - the whole translator list is passed to `setTranslator`;
  - records with only a PMID (a PubMed number) are looked up 200 at a time;
  - a record whose lookup fails is imported by hand-mapping instead, for each reason class, and each such fallback is logged and counted;
  - the missing-abstract repair runs after either path;
  - the preprint server name is written without changing the item type the translator chose;
  - each created item records which path produced it;
  - the preference strings exist in both languages.
- **Stopped and reported:**
  1. **Per-run counts in the visible import summary.** The counts are computed, summed per run and logged. Showing them in the summary needs `src/pipeline/searchImport/types.ts`, `src/pipeline/searchImport/searchImportPipeline.ts` and `src/ui/viewModels/searchImportViewModel.ts` (the last is P2-T17's file). All three are outside Files, so they were not edited.
  2. **The Europe PMC side of the PMCID route** (PMCID is a PubMed Central number). No document gives a Europe PMC query form for a PMCID (rule 4). The import side is built behind a resolver seam (a swappable function); with no resolver configured, a PMCID-only record goes straight to hand-mapping.
  3. **The per-record timeout value.** No document gives a number (rule 4). The timeout mechanism is built and tested but has no default.
- **Live network requests: not 0.** The finished code and the passing test runs made none. One mutation run (mutant I1, section 5) did. That mutant sent every import in the whole integration suite through Strategy B, and the other test files use Zotero's real `Translate.Search`. The evidence:
  - the preprint round-trip spec received real server metadata ("Molecular Biology" for the bioRxiv record, "Intensive Care and Critical Care Medi…" for the medRxiv record);
  - two 100-record imports slowed from about 0.5 s to 29.7 s and 32.3 s.

  The requests were not counted; they may number several hundred. The other mutants were checked: each one changes only code that runs when the Strategy B option is supplied, which only the new spec does, and it always supplies a fake lookup object.

## 6. Contradictions with the card or corpus

1. **`provenance.fieldOrigin` cannot name the import path** (step 9). `docs/07` §5.1 types `WorkProvenance.fieldOrigin` as field name → `SourceId` (a literature database id), and `isWorkProvenance` rejects any other value. Nothing persists a work's `fieldOrigin` per item either. The path is therefore recorded in `ImportReport.createdVia`, aligned with `createdItemIDs`. Placing it in persisted provenance needs a `docs/07` decision.
2. **The summary strings belong in `mainWindow.ftl`, not `searchDialog.ftl`.** The searchDialog bundle's own header says the import summary messages live in `mainWindow.ftl`, and no id may be declared in two bundles. The new summary ids sit beside `research-helper-import-summary`.
3. **The card's Verify-with `diff` cannot pass.** It names the dropped `preferences.ftl` bundle. The `searchDialog` id sets already differed on the starting tree, by design: pending Korean strings are commented stubs on `KO_PENDING_REVIEW`.
4. **Step 2 says the preference is read in `stages.ts`.** `WritingItems` (the import's write stage) is entered in `searchImportPipeline.ts`, which is outside Files. The writer reads the preference on its first `writeBatch`. That call is the first thing `WritingItems` does, so the read happens once, at entry (`docs/07` §12.1).
5. **No document gives the per-record timeout number** (step 7, `docs/07` §12.1).
6. **No document gives a Europe PMC PMCID query form** (step 6). The `docs/02` §4.3 field table lists only `DOI` and `EXT_ID` (a PMID). `PMCID:` appears only in `plan/00` item 132 and P2-T03's report.
7. **`docs/01` §6.2's `saveAttachments`:** the code passes `true`, as in the `importByIdentifier` reference implementation. That value means Strategy B also downloads any open-access PDF.

## 7. What was not checked

- **A real translator lookup against live services** (deliberately not run). The only real-API check is that the four methods exist on Zotero 10.0.3's `Translate.Search`.
- **Whether a real `{ PMID: [...] }` batch returns items carrying a native `PMID` field.** `pmidOfItem` also reads a `PMID:` line from the item's `extra` field as a fallback.
- **A timed-out lookup that later finishes:** it may still save its item, alongside the hand-mapped copy. The duplicate risk exists only once a timeout value is chosen.
- **A lookup that saves more than one item:** the extras stay in the collection, uncounted, and are logged at warn.
- **Cancelling mid-lookup:** items the translators already saved stay, and the thrown error carries no counts.
- **Strategy B items do not get the `research_helper` tag or the superseded-preprint tag** that hand-mapped items carry. The card did not ask for them.
- **Korean wording:** left for a native-speaker review under gate G-41.
