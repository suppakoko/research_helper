- **Adapters.** All four adapters have `validateCredentials()`. Each sends its own provider's model-list call through the existing HttpClient and its own `send`/transport, never a completion:
  - OpenAI and Anthropic: `GET /v1/models`.

- **How each answer is read:**
  - 2xx: ok, with the models.
  - 401, and Gemini's 400 `API_KEY_INVALID`: rejected.
  - 403: forbidden.
  - 429: ok (the key was accepted).
  - Anything else: inconclusive.

CONTRADICTIONS/FINDINGS
1. **Suggestions load when the list is first opened, not "on pane load"** (step 5). Opening the pane would otherwise make a live request to openrouter.ai, plus each configured provider's list with its key, from Settings and from the integration spec that opens the pane. That breaks the "no live request in tests" rule and sends traffic the user did not ask for. The docs/08 note records this; the owner may want to confirm.
2. **The card's Files list could not hold everything.**
   - `gemini.test.ts` and `openrouter.test.ts` asserted the old refusal.
   - `sessionStore.test.ts` checks every keychain export and every preference it writes.
   - `typings/i10n.d.ts` is generated.
   - All of these needed edits. preferences.xhtml was not touched: the suggestion lists and the price section are built as DOM in preferences.js, inside the existing `rh-prefs-providers` groupbox and beside the existing model inputs.
3. **The 429 rule is applied by HTTP status.** An OpenAI `insufficient_quota` 429 or an Anthropic spend-cap 429 (`QuotaExceededError`) also counts as "key accepted". This follows the card's "429 → ok"; a key with no credit still shows as accepted.
4. **The adapters' failure `messageKey` is the error's own `rh-error-*` id**, not a pane id. That satisfies "401 distinct from 403", and the pane maps it. The adapters keep their usual 3-minute LLM attempt timeout and the client's 429/5xx retry budget, so a Test against a rate-limited or failing host can take up to about 90 s before it reports. There is no per-request retry override, and adding one would mean changing the HTTP client.
5. **Inconclusive outcomes are persisted when the service answered** (5xx, unreadable answers), but not when no answer came. The source checks follow the same rule: `classifyFailure` now says `no-answer` for a failure with no HTTP status, and a test was updated accordingly.
6. **The key-present status line is now slightly wrong.** `research-helper-prefs-key-present` still says "A key is stored. Not tested yet this session." With stored results it should read "not tested yet". I left it unchanged, because changing it would invalidate its pending Korean.
7. **The caller of the mid-job 401 policy is not wired.** `PooledRunDeps.onCredentialRejected` has no product caller yet. P3-T29 (`summarizePipeline`) should bind it to `markProviderKeyRejected(String(error.context.providerId), clock.now())`. The pause and the single notification happen even without it. No `JobNotifier` implementation exists yet, so the notification's wording belongs to the card that builds that surface.
8. **P3-T15 finding 1: nothing moved.** The Gemini paid-tier checkbox already sits in the Gemini block, two rows below the model field. Moving it would need a markup change.
9. **Other model fields now trigger a pref write too.** Picking a suggestion fires `input`/`change` so Zotero's binding stores the model. This was checked only against fake elements, not against Zotero's real `_syncToPrefOnModify`.
10. **The rotation-reset rule is documented only in keychain.ts.** The `SecretStore` port (`src/core/secretStore.ts`) says `set`/`clear` maintain the `keyPresent` flags, but does not say they reset the validation rows.
