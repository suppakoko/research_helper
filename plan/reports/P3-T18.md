P3-T18 report: text acquisition tiers 1–2 (abstract, attachment text)

VERDICT
P3-T18 is done. One Done-when line is met in substance but not in its literal wording. The plugin now gets a cleaned-up ("normalized") abstract (Tier 1) and the attachment's text (Tier 2) for a Zotero item. A fully indexed PDF is read from Zotero's index cache with zero calls to Zotero's PDF text extractor (PDFWorker). A password-protected PDF, a corrupt PDF or a missing file falls back to the abstract with a warning and never throws. The content hash is SHA-256 of the exact text sent. Nothing calls the indexer, reads the cache file directly, or downloads a file. The exception is the "over the cap, none [re-extractions]" line: the card's partial-index rule rests on a wrong belief about Zotero. Zotero's attachmentText getter does not return the truncated cache when an attachment is only partly indexed; it extracts every page itself. I measured this in the installed Zotero 10.0.3 source and in a live run. So when the page count is over the cap, the code makes one bounded extraction of only the pages already indexed and sets truncated to true. That is the outcome the design decision asks for ("accept the truncated cache"), but it is one extractor call, not zero. The full contradiction is below. Final state: typecheck, lint:check, eslint, all 56 unit and contract test files (2964 tests), build, and the integration suite (181 passed) are all clean. That integration result rests on 2 clean runs (runs 4 and 5) of the final code. No mutant is left in the tree. Nothing is committed.

CONTRADICTIONS
1. Card step 4 and Done-when "INDEX_STATE_PARTIAL… over it, none, and truncated is true", against Zotero itself. attachmentText reads the cache only when isFullyIndexed() is true; on a partly indexed attachment it calls getFullText(this.id) with no page limit (installed omni.ja, Zotero 10.0.3, plus the measurement above). Following the card literally would extract twice under the cap. Over the cap it would extract every page and still label the text truncated, which would be false. Reading the cache file directly is forbidden. As built: under the cap, one all-pages read; over the cap, one read limited to indexedPages, truncated true. The owner should confirm this reading of D-06-3 and reword that Done-when line. docs/06 §3.3.4 now records the measurement.
2. AcquiredSource.estTokens: the card says "Fill AcquiredSource", but the one estTokens belongs to P3-T06 (src/llm/shared/tokenEstimate.ts, still being written) and must be exported from one module only. acquireSource therefore takes `estimateTokens` as a required option; P3-T25 should pass estTokens.
3. docs/06 §13.5 said a missing file makes attachmentText return ''. Measured: for a PDF with no cache it throws "Could not read `false'"; '' happens only when the attachment has no content type. Corrected in docs/06.
4. docs/06 D-06-3 names the flag `sourceTruncated`; §3.6, docs/07's StoredSummary and the card say `truncated`. I used `truncated` and recorded the alias in docs/06.
5. The card's Files list has no home for the grep test, and its Verify filter (`normalizeAbstract`) would not run one placed anywhere else. I placed it in acquire.test.ts (see Files).
6. Smaller design choices, for the owner to see:
   - SourceTier `fulltext_pdf` is also used for EPUB, HTML-snapshot and plain-text attachment text, because docs/06 fixes a four-member union.
   - Keywords taken from the abstract (step 3) are returned by normalizeAbstract but have no field on AcquiredSource.
   - The md5 fallback is written `md5:<hex>` with a `content_hash_md5` warning.
   - `includeFullText: false` (for summary.fullTextMode "never") is my addition.
   - On Tier 2 the abstract and the attachment text are joined by a blank line ("\n\n") that this code adds; the attachment text itself is never trimmed, re-wrapped or split.
