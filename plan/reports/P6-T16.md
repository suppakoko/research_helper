## What was built

- **`src/pipeline/audioReport/audioReportPipeline.ts` (new): `createAudioReportPipeline`.**
  - **Two halves, as the report job has.** `prepare(input, ctx, surface)` runs with no job record and makes no TTS
    request. `execute(prepared, ctx, surface)` runs in the record's context. `audioJobInput(prepared, now)` is the
    record's input: the run's input with the egress log of what the user confirmed. It refuses a run that was not
    confirmed.
  - **`prepare`'s order.** `audio.enabled` off → refused `disabled`; no stored report → `no-report`; a read-only
    library or a missing collection → `read-only` / `no-collection`; the tier → `tier-refused`; no Gemini key →
    `no-key`. Only then are the language, the voice and the TTS model resolved, and the script step or the stored
    script's plan priced. A refusal is a value, not a throw.
  - **`execute`.** The script call (when due), the script stored at once on the job's record, the padded size check,
    the second confirmation, synthesis with "chunk n of N", delivery, and the attachment key stored. A budget stop
    pauses the record and asks; "continue" raises the ceiling and re-sends the pending chunk.
  - **No request without a log.** Every script and TTS request passes a `beforeSend` hook that refuses to send when
    the record carries no audio egress log.
  - **Failures** go through `classifyAudioFailure`. A cancel discards the audio and keeps the script. A shutdown
    leaves the record for `recover()`.
  - **Caller:** the report window's session (`createReportWindowSession`, `P6-T17`). **Constructed in:**
    `buildPipelineSet` (`src/bootstrap/registerPipelines.ts`).
- **`src/zotero/db.ts`.** `ReportStore.latestForCollection(libraryID, collectionKey)` (the newest record by
  generation time; a tie goes to the smaller id) and `ReportStore.companionOf(report)` (the other-language record of
  the same run, or nothing).
- **`src/bootstrap/pluginDatabase.ts`.** The database wrapper forwards the two new methods. This file is outside the

- **`src/bootstrap/container.ts`.** Passes the TTS client `registerProviders` builds, the key reader over

- **`src/core/secretStore.ts`.** A comment beside `"tts.gemini"`: unused, because TTS reads the chat key

## Decisions taken (each DECIDED 2026-11-17, coordinator, under `plan/00` §6 item 313)

All ten are in `docs/07` §12.6's note of that date. In short:

1. Two halves, with the record enqueued between them by the session, and the `beforeSend` egress-log check.
2. `prepare`'s refusal order, and the script model put through the privacy check before the first confirmation.
3. The TTS model is resolved in `prepare` (owner question: item 385).
4. Both size checks use the estimate with headroom.
5. The companion record is found by `companionOf` only when the script's language is not the report's; the script
   and the key are stored on the job's own record.
6. `latestForCollection`'s tie goes to the smaller id.
7. The key is read once, for its fingerprint only. The known fingerprints are those of stored `audioReport` jobs, so
   the second confirmation finds the job's own record and does not repeat the first-use notice.
8. A confirmed tier answer is written at once, so the question is never asked twice.
9. A budget stop pauses and asks, as the report job does.
10. The output carries what the window's offers need; the attachment title is the surface's, English until
    `P6-T17`; `PipelineContext.tts` stays `undefined`.

## Findings

1. **A restart marks the job `failed`, not `cancelled` (not a card).** `resumable` is `false`, so `JobQueue.recover()`
   marks a job the app quit during `failed` with `NOT_RESUMABLE_CODE`. This card's decision of 2026-11-16 says
   "marked cancelled". The stored script stays either way, which is what that decision protects. It does not block a
   finishing condition of Phase 6.
2. **The model list is read before the confirmation.** With `tts.model` empty, `prepare` reads Gemini's model list:
   one request carrying the key and no user content, to the host the notice then names. Recorded as `plan/00` §6
   item 385, with a draft answer that is not adopted.
3. **`PipelineContext.tts` stays `undefined` (not a card).** The TTS client reaches the pipeline through its
   construction deps, as `docs/07` §4.4's note already allows.
4. **A file outside the Files row.** `src/bootstrap/pluginDatabase.ts` had to forward the two new store methods.
