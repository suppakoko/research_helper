Why: acquireZoteroSource now runs the cleaning pass. The spec's generated PDFs put a marker line `RHP3T18-PAGE-0N-OF-0M` first on every page. With the digits stripped, that line is identical on every page, so step 2 correctly deletes it as a running head. The specs' `pagesPresent(...)` page-number checks then find no pages. The fully indexed spec also asserts `warnings` equals `[]`, but a 3-page generated PDF is under the probe's 1,500-character minimum, so it now gets `ocr_suspected`. I could not run that spec and it is outside my file list, so I did not edit it. It needs a follow-up: either vary the marker's non-digit text per page, or call acquireSource without cleaning, and expect `ocr_suspected`. The password, missing-file and content-hash specs should be unaffected.

What is built:
- Tier 3 has an open-access gate (the core record must show both "Y" fields) in front of a fullTextXML fetch that only the gate can reach. All requests go through the one installed HttpClient, so there is no second Europe PMC pool.
- `fullText.preferJATS` is honoured, with fallback to Tier 2.
- The cleaning pass follows docs/06 §4.1 steps 1–7. De-hyphenation is "do nothing", with no regex. `\n` is never treated as a paragraph boundary. The 8–60 % reference check is applied.
- The OCR probe only warns and never demotes. Its thresholds are constants marked PROPOSAL, or provisional for the 0.80.
- The §4.2 language check is in place.
- Tier 4 produces a stub through a structural no-LLM gate, and the stub validates against paper-summary.v1.json.
- The §13.1 recoveries are in, with write-back gated on one consent per run, built as a callback.

Every Done-when line has a passing test except the last one. `npm run typecheck` exits 0. `lint:check` and `npm run test` fail only on other agents' files (see RUNS).
