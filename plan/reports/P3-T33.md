How and where the database now opens
- installServices step 6c calls installPluginDatabase. That calls openPluginDatabase() in line, which is synchronous: Zotero.DBConnection connects only on its first query. installServices therefore opens the file at its point in startup, and the open needed no design change.
- The migrations are queries, so they are not synchronous. They run in the background as graph.database.ready, just as they did in openProvenanceStore, to keep the NFR-10 startup budget of 200 ms. This is the smallest correct change: only the owner of the open moved.
- Every store waits on ready:
  - the cache's connection getter awaits it;
  - attachJobs chains onto it, then attaches createJobStore(connection) and starts jobs.recover();
  - publishProvenanceStore builds the provenance index from ready.provenance.
- Teardown is registered at step 6c, so it runs after the later registrations (the search window host, the published provenance store, the menus). Its order is:
  1. await ready;
  2. cancel the scheduled prune (about 30 s after startup, then every 6 hours, on the graph's clock);
  3. cache.close(), which waits for operations still running;
  4. await the job recovery;
  5. jobs.detachStore();
  6. closeDatabase(true).
- If the open or a migration fails, ready resolves to undefined, the queue stays without a store, the cache stores nothing, and one error line is logged.
- The same graph and connection are confirmed live in Zotero by the integration spec (open.connection === api.provenance.database). The search window's provenance store, the job store attach with recover(), and the disable/enable lifecycle spec all pass.

Contradictions
1. §4.1 says an omitted ttlMs never expires, while §9.2 gives each namespace its own time-to-live. The code applies §9.2 when ttlMs is left out, and §4.1 is corrected in place.
2. §9.4's score formula, `lastAccess + hits * bonusMs - costWeight`, subtracts the very bonus that is meant to keep expensive entries longer, and gives no numbers. The code adds the bonus. It uses 1 hour of recency per hit, and a retention bonus of 30 days for summary and embedding and 0 for every other namespace. Owner to confirm the numbers; they are recorded in docs/07 §9.4.
3. The P3-T34 report and docs/07 §7.6 said P3-T33 fills skipCached. It cannot without summaryKey, which is P3-T26's. The doc is corrected, but P3-T26's card does not name the guard yet.
4. §9.1 joins key parts with "|", which is ambiguous when a part contains "|". The generic cacheKey hashes a stableStringify'd array instead. The specific key builders, including summaryKey, are P3-T26's, which may keep §9.1's form.
5. §9.4 step 4 says never to evict a running job's entries, but nothing yet exposes which jobs are running. createSqliteCache takes a pinnedTags hook (work:<key> tags), tested here. installServices passes none for now; the job runner (P3-T17, P3-T35) should supply it.
6. The card's Verify filter "core/cache|provenanceRerun" matches nothing in this Vitest version, as P3-T34 and P3-T36 also found. Working form: `npm run test:unit -- cache provenanceRerun jobQueue container`.
7. Item 255 listed that the job store's ON CONFLICT upsert had not been measured inside Zotero. The cache's upsert uses the same SQLite feature, and the new integration test now exercises it in Zotero 10.0.3, where it passes.
