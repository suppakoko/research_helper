**Startup reconciliation as built**
- `installServices` step 2 calls `installSecretStore`, before the rate limiters are built, as before.
- After the keystore check passes, `installSecretStore` calls `reconcileKeyPresence()`.
- That function first works out all six flags from `hasSecret`, which never decrypts. Only then does it write each flag with `setPref`. So if the login store fails part-way through, every flag stays as it was, rather than some being updated and some not.
- `gemini.keyPresent` is true when either `llm.gemini` or `tts.gemini` is stored. The same rule now applies when a single key is set or cleared through `refreshKeyPresence`. Without that, clearing `tts.gemini` would have written `false` while an `llm.gemini` key was still stored.
- If reconciliation throws, the store is still returned and one warning is logged. The flags it wrote are flag names with true or false, never a value.
- If the keystore check fails, nothing is reconciled, as before. That case is P3-T03's.
- Following up P3-T06 contradiction 12: a flag that was already wrong at startup is now corrected. A key removed outside Zotero while Zotero is running still leaves its flag wrong until the next start. So each adapter's `isConfigured()` should still check the keystore, which is the adapter cards' job.

**The uninstall question (not measured)**
- **Measured from the code:** `onShutdown` in `src/hooks.ts` deletes `Zotero.__addonInstance__`. Its teardown also detaches the preference store (`installServices` step 1).
- **Not measured, and needs Zotero:**
  - whether Gecko calls `shutdown(ADDON_UNINSTALL)` before `uninstall()` for an enabled plugin;
  - whether the plugin file is still readable during `uninstall()`;
  - whether `data.rootURI` is present for `uninstall`.
- **Built to be safe either way:**
  - `uninstall` returns at once unless the reason is `ADDON_UNINSTALL`. Gecko also calls the old version's `uninstall()` with `ADDON_UPGRADE` or `ADDON_DOWNGRADE`, and clearing then would delete keys on every update.
  - If the plugin object is still on `Zotero`, `uninstall` calls `hooks.onUninstall()`.
  - Otherwise it loads the bundle again into a fresh context, as `startup` does, using `data.rootURI` and falling back to `data.resourceURI.spec`. It never calls `onStartup`, so nothing is registered, and it deletes the plugin object that load created.
  - `clearAllSecretsOnUninstall` sets up a Zotero preference store just for the sweep if none is set up, and detaches it afterwards. Without that, the first `clearSecret` would remove its login and then throw on the flag write.
  - `uninstall` never throws. A failure becomes one Debug Output line that holds a count or an error message, never a value.
- **Still open, to confirm in Zotero:**
  - a real uninstall of a profile holding a synthetic key leaves `listStoredIds()` empty;
  - the same for a plugin that was disabled first;
  - an upgrade keeps the key.

**Contradictions**
1. **The shared Gemini flag needs a rule the card did not state.** If only the key just written were checked, `tts.gemini` and `llm.gemini` would overwrite each other's flag. Built as "either key is stored". `docs/07` §8.5 does not say this explicitly.
2. **The card says "verify yourself; if `uninstall()` cannot reach the keychain code, stop and report".** The coordinator's brief overrides that: build it safe either way and record the question. Done that way; the question is open above.
3. **`uninstall()` can be called for an upgrade.** `docs/09` §2.5 says `uninstall()` clears every `SecretId`, without saying that Gecko also calls it with `ADDON_UPGRADE` or `ADDON_DOWNGRADE`. Taken literally, that would delete keys on every update. The code clears only for `ADDON_UNINSTALL`.
4. **`docs/09` §2.5 also says `uninstall()` clears "every plugin pref".** That is not in the card and was not built. The comment in `addon/bootstrap.js` still says Zotero removes preferences itself, and that claim has not been checked.
5. **Files outside the card had to change:** `src/hooks.ts`, three new unit test files, and three test fakes. The reasons are under Files.
6. **The card guessed that `installSecretStore` is not exported, and it was not.** It is now exported, so that both the unit test and the integration test can call it directly. That was a one-word edit.
7. **The pane's `clearAllKeys` in `src/ui/prefs/preferencesPane.ts` still has its own copy of the sweep loop.** It could call `secrets.clearAll()` instead. That file is outside this card; P3-T04 could do it.
8. **The doc comment on `probeAndRecordBackend` in `keychain.ts` still says "Nothing calls this at startup yet".** That was already out of date before this card and was left alone.
