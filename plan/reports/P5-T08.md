## COORDINATOR-LEVEL DECISIONS YOU TOOK

Each is "DECIDED 2026-11-02 (coordinator, under plan/00 §6 item 313)". The first three are written with that wording: 1 in `elink.ts`, 2 and 3 in `docs/07` §4.2. Decisions 4 to 6 are recorded as described behaviour and need the same wording when the coordinator records them in `plan/00`.

1. **The key.** The builder takes an optional `apiKey`, placed between the seeds and the identity parameters, as `esearch` and `efetch` do.
   - The adapter sends it whenever the key store holds one, because `HOST_POLICIES` paces NCBI at 8 per second with a key and 2.5 without. An unkeyed request at the keyed pace would run into NCBI's lower limit.
   - An unkeyed URL stays byte for byte the same, so the fixture name still matches. A keyed URL hashes to another name, as `esearch` does, and fixtures stay unkeyed.
2. **Strategy and missing PMID.** `"similar"`, `"auto"` and no strategy read the list. Any other strategy, or a seed with no PMID, gets an empty page with a warning and no request. I first chose a `RangeError` and changed it to match `P5-T09`'s decision in `docs/07`, so `P5-T12` sees one behaviour.
3. **`fromDate`.** It filters after hydration through `applyClientRecencyFilter`, and undated records are kept, so a page can hold fewer than `limit` records.
4. **Seed cap.** `PUBMED_ELINK_MAX_SEEDS` is 10, from `docs/05` §7.3, and more seeds throw a `RangeError`. It also bounds the GET's length, which `P5-T04` flagged. No NCBI limit on `id=` parameters is recorded.
5. **Rank and score.** `rank` is the position after the seed is dropped, and ranks can have gaps when `efetch` returns no record. The maximum is taken over the whole list, not the slice. `elink`'s order is kept and not re-sorted.
6. **What is refused and what is tolerated.**
   - A linkset that does not name exactly one seed throws `ParseError`.
   - A top-level `ERROR` throws `SourceError`.
   - A link with no digit id or no positive score is left out and counted in a warning.

## CONTRADICTIONS/FINDINGS

1. **Request counts in `docs/05`.** §4.4 ("10 seeds → 10 requests"), §7.3's row b and §9.3's rank 3 count one `elink` per seed, but one request carries up to 10 seeds. The same rows do not count the hydration, which is one `efetch` per 200 distinct neighbours. At limit 100 over 10 seeds that is up to 1000 PMIDs, so up to 5 `efetch` calls. The `docs/05` §4.3 note records this; the rows themselves were not rewritten. `P5-T23`'s "a budget of 12 runs (a) and (b) fully" needs reading against the real cost.
2. **`P5-T12` step 3 against this adapter.**
   - That step hydrates survivors through `lookup`, naming `efetch` as a fallback, but PubMed declares `lookupById: []` and has no `lookup`.
   - `RelatedPage.records` must be records, so this adapter hydrates before the merge, and PubMed's rows need no second step.
   - The adapter cannot filter owned papers before hydrating, which is the tension with `docs/05` §9.1 item 2 and `P5-T12`'s **Do NOT**. A small `limit` is what controls it.
3. **`docs/05` §4.3 against §9.1 item 2.** `elink` returns ids and scores only, so a date filter cannot run before hydration.
4. **Stale line outside my Files.** The `src/sources/types.ts` header still says "No adapter implements it yet". `P5-T07` already corrected the same line in `docs/07`.
5. **A test defect found by the sweep.** A JavaScript object literal sorts integer-like keys, so my hand-written "reversed" body was not reversed and the attribution test proved nothing. The body is now written out as an array. Anyone writing such bodies for PMIDs should do the same.
