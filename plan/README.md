# research_helper — Execution Plan

> **What this folder is.** The executable layer under
> [`docs/11-implementation-roadmap.md`](../docs/11-implementation-roadmap.md).
> The roadmap says *what each phase achieves and why*. This folder says
> *exactly what to do next*, as discrete task cards that can be handed to
> Claude Code one at a time.
>
> **Last updated:** 2026-09-09 · **Status:** no code written yet; every task is `TODO`.

---

## 1. Who executes this

**Claude Code implements; a human gates.** Every task card is written to be
pasted into a Claude Code session as-is. It names the files to touch, the design
sections to read first, the acceptance criteria, and the command that proves the
task is done.

Some tasks cannot be finished by an agent — they need a human to enter a
credential, approve a spend, click through a GUI, or judge Korean prose. Those
carry a **Human gate** and are listed in
[`06-human-gates.md`](06-human-gates.md). An agent reaching a gate must **stop
and report**, never work around it.

## 3. Task ID scheme

`P<phase>-T<nn>` — `P0-T01`, `P3-T14`. IDs are permanent: never renumber, never
reuse. A task that is dropped stays in the file marked `DROPPED` with the reason.
A task discovered mid-phase gets the next free number in that phase, even if that
puts it out of dependency order in the file.

Other identifier namespaces referenced from task cards are owned elsewhere and
must resolve there: `FR-*` / `NFR-*` in `docs/10`, `R-*` and `V-*` in `docs/11`,
`D1`–`D10` in `docs/00` §3, `D-06-*` in `docs/06`, `DR-*` in `docs/06` §5.4
("Decision rule — when to skip full text"; `DR-1` is cited six times in
`plan/04`, including in `P3-T25`'s title), prompt IDs in `docs/12`.

## 4. The task card schema

Every task uses exactly this shape. Fields are never omitted; write `none` or
`n/a` rather than dropping a row.

````markdown
### P0-T03 — Imperative title, under 60 characters

| Field | Value |
|---|---|
| **ID** | `P0-T03` |
| **State** | `TODO` |
| **Depends on** | `P0-T01`, `P0-T02` |
| **Blocks** | `P0-T07` |
| **Retires** | `V-3`, part of `R-11` |
| **Implements** | `FR-6`, `NFR-1` |
| **Estimate** | 0.5 d |
| **Human gate** | none |

**Goal.** One sentence. What is true after this task that was not true before.

**Read first.**
- `docs/07-architecture-and-data-model.md` §4.3 — the `LLMProvider` contract this must satisfy
- `docs/01-zotero-plugin-platform.md` §8.1 — `Zotero.HTTP.request` option table

**Files.**
- create `src/core/http.ts`
- modify `src/index.ts`
- create `test/unit/http.spec.ts`

**Do.**
1. Numbered, ordered, each step independently checkable.

**Do NOT.**
- Named traps, with the reason. Pulled from the design docs' gotchas.

**Done when.**
- [ ] A verifiable assertion, not "it works".
- [ ] `npm run typecheck` exits 0.

**Verify with.**
```bash
npm run typecheck && npm run test:unit -- http
```

**Notes.** Gotchas, links to the specific `> **Unverified:**` markers this task
resolves, and anything the implementer will otherwise rediscover the hard way.
````

### Field rules

- **State** — one of `TODO`, `IN PROGRESS`, `BLOCKED`, `DONE`, `DROPPED`. Only
  the human changes state to `DONE`.
- **Depends on / Blocks** — task IDs only, and they must be mutually consistent:
  if `A` blocks `B`, then `B` depends on `A`. `00-task-index.md` is generated
  from these and will catch mismatches.
- **Human gate** — exactly two spellings, because `00-task-index.md`'s gate column
  is generated by matching on them. A gated card writes ``**Yes** — <what the human
  must do>``: the word `Yes` capitalised, bold, followed by an em dash and the
  requirement in plain prose *outside* the bold. An ungated card writes the bare word
  `none`, with nothing after it — if a card needs to explain why it is ungated (because
  it inherits a predecessor's gate, for instance), that explanation goes in `Notes`,
  not in this cell. `**yes**`, `**yes — …**` and `none — …` are all defects.
- **Read first** — **exact sections, with a clause saying why**. A bare document
  name is not acceptable: the corpus is 24,027 lines (`wc -l docs/*.md`, i.e.
  `docs/00`–`docs/13`, as of 2026-09-09) and an agent told to "read doc 07" will
  read the wrong part of it.
- **Files** — every path prefixed `create`, `modify`, or `delete`. A task that
  cannot name its files is not decomposed enough. Within a phase, a path is
  `create`d by exactly one card and `modify`ed by the rest. **Across the Phase 0
  boundary the rule is relaxed, deliberately:** Phase 0's cards are spikes, they
  are written to be executable before the later phases' IDs are stable (see
  `02-phase-1-pubmed.md` §1, "Phase 0 dependency", on why Phase 1 names no `P0`
  ID in **Depends on**), and several of them stand up a first, minimal version of
  a module the shipping phase then writes properly. Where a Phase 1 or Phase 3
  card says `create` for a path a Phase 0 card also created, **the later card
  wins and its `create` means "write the shipped module, replacing whatever the
  spike left there"**. The sixteen paths this applies to are
  `src/model/ids.ts`, `src/core/http/client.ts`, `src/core/http/userAgent.ts`,
  `src/bootstrap/container.ts`, `src/bootstrap/registerUI.ts`,
  `src/i18n/ftl.ts`, `src/llm/shared/sse.ts`, `src/zotero/zoteroApi.ts`,
  `src/zotero/itemMapper.ts`, `src/zotero/collectionOps.ts`,
  `src/zotero/prefStore.ts`, `src/zotero/keychain.ts`, `src/zotero/fulltext.ts`,
  `test/integration/l10n.spec.ts` and the two `mainWindow.ftl` bundles. Nothing
  in a spike version of those files is load-bearing; nothing outside this list
  may be `create`d twice.
- **Do NOT** — never empty for a task that touches an area where the design docs
  record a trap. This field is where 8 rounds of research review earn their keep.
- **Done when** — mechanically checkable. "Summaries look good" is not a
  criterion; "every returned `PaperSummary` validates against the §6.2 JSON
  schema" is.
- **Verify with** — a command that exits non-zero on failure, or the literal
  steps of a manual check when no such command exists.

## 5. Execution protocol

When Claude Code is handed a task card:

1. **Read the `Read first` sections before writing code.** They exist because
   the obvious implementation is wrong in a documented way.
2. **Do not widen scope.** If the task needs something not in `Files`, stop and
   say so rather than inventing it. Out-of-scope discoveries become new task
   cards, not silent extra work.
3. **`docs/07-architecture-and-data-model.md` is the sole authority for types
   and for the preference schema (§8.5).** Docs 02 and 03 contain deliberately
   divergent working-name sketches of `QueryNode`, `QueryField`, `WorkType`,
   `ModelInfo`, `LLMProvider` and `LLMError`, each carrying a "doc 07 wins" note.
   Typing straight from those blocks builds a parallel, wrong type system.
4. **Never hardcode a model ID, price, or rate limit.** Model IDs come from the
   provider's live catalogue (`docs/03` §5.5), rate limits from
   `docs/07` §7.3, preference defaults from `docs/07` §8.5.
5. **Never write a credential to a preference.** Decision D5. Secrets go through
   `Zotero.OSKeyStore` + `Services.logins` only; prefs hold `*.keyPresent`
   booleans. A task that appears to require otherwise is a defect in the task.
6. **Run `Verify with` before reporting done**, and paste the real output. If it
   fails, report the failure — do not adjust the criterion to match the code.
7. **Stop at a human gate** and say precisely what you need.

## 6. Conventions

- **Repository.** Not yet initialised. `P0-T01` creates it. Default branch
  `main`; work on `phase-N/<task-id>` branches; the plugin ID is
  `research-helper@suppakoko.github.io` (D9) and must never change.
- **Every phase ends installable.** Incomplete work hides behind a pref, never
  behind a broken menu item (`docs/11` §0 principle 5).
- **Tests ship with the task, not after it.** A task whose `Files` list has no
  test file needs a reason in `Notes`.
- **Cost.** Any task that spends money on an API carries a Human gate and states
  the expected spend.

## 7. Estimates

Effort figures are **rough estimates for one experienced developer** new to
Zotero plugin development, in developer-days of one focused 6-hour day, matching
`docs/11`'s convention. They exclude review latency and time waiting for API key
approvals.

**The direction of authority changed on 2026-09-09, and only for the decomposed
phases.** Decomposing Phases 0–3 put every phase 47–72% above `docs/11`'s
figure, in every case because work `docs/11` listed as a phase deliverable was
never priced. The rule below was applied, `docs/11` §1 was re-estimated from the
card sums rather than the cards being shaved, and the bands it now publishes for
Phases 0–3 are **derived from these cards**: low end = the phase's task sum,
high end = that sum × 1.4 (`docs/11`'s own ±40% convention), rounded to the
nearest whole day — e.g. Phase 2's 24.25 × 1.4 = 33.95 → the published 24.25–34.
So for Phases 0–3 the cards are the measurement and
`docs/11` records it; a task sum that no longer equals its phase's low end means
a card estimate moved and `docs/11` §1, its effort-summary table, and §2's
critical path have to be re-derived. `00-task-index.md` §1 carries the current
sums (15.50 / 18.75 / 24.25 / 23.50 d, 82.00 d for Phases 0–3).

**Phases 4–7 are not decomposed**, so for them `docs/11` remains authoritative:
its figures there are the old ones scaled by the ×1.50 correction factor these
four decompositions measured, and `docs/11` flags them as inference (risk R-23).
When one of those phases is decomposed, expect its per-task sum to land above
the scaled figure — decomposition surfaces work that a phase-level guess hides.
If a phase's task sum diverges from `docs/11` by more than ~30%, that is a
signal to re-estimate the phase in `docs/11`, not to quietly adjust the tasks;
that is the rule Phases 0–3 were corrected under, and it is not to be silently
reverted.
